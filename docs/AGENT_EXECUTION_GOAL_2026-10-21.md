# Agent 与两个业务模块的执行目标

目标：在当前 App 中，使 Agent 能根据明确用户意图调用资产和扫描模块的真实业务接口，完成范围与权限校验、持久任务创建、进度读取、暂停/恢复和结果核对。

## 验收顺序

1. 资产证书补采：复查实际执行、断点恢复、唯一指纹与成功资产数的区别，以及来源字段和原始数据保护。已交付记录见 `CERTIFICATE_BATCH_EXECUTION_2026-10-21.md`；新改动仍须回归。
2. 扫描通道：接到当前桌面扫描 owner，不能把 Node 草稿当作扫描，也不能把独立原生服务的项目编号当作桌面项目编号。至少支持当前项目真实任务列表、状态、由库存资产创建原生草稿，以及原引擎启动/暂停/恢复。继续沿用原引擎的授权、预算、并发、模型、审计与恢复限制。
3. Agent 调度：明确区分读取、创建草稿、开始执行和暂停恢复；一次控制后读取真实状态，不逐资产调用模型，不在一轮持续轮询，不擅自重发结果未知的付费操作。
4. 跨模块：资产交接只传当前项目已存在的资产标识，由业务 owner 读取 URL；不信任模型提供的数据库路径、项目覆盖或资产归属声明。结果回到原任务与原项目展示。
5. 故障与体验：优先处理丢授权/重复授权、版本变化、范围撤回、空队列、重启、过期响应、终态冲突、配置重叠，以及会阻断操作的 UI；按证据排序，不无限扩展到无关重构。

## 每阶段交付要求

- 保留配置、密钥、历史资产、人工结论、CAS 和已有授权；真实数据变更前建立一致备份。
- 不更改 VPN/代理，不恢复 HackerOne，不自动消耗 Hunter 积分。
- 先做适用回归，再更新 `/Applications/Oviraptor.app` 和内置组件；真实项目复测与回归/合成测试分开记录。
- 模型不能获得内部桥 bearer、文件路径或配置密钥。执行权限与读取权限分开，已有权限不重复申请。
- 原生任务接受启动不等于完成；暂停中不冒充已停；证据命中不等于资产归属；未覆盖的边界必须写明。
- 通过检查的改动推送当前功能分支，不强推、不擅自合并主分支。Goal 在这些闭环完成前保持 active。

## 当前发现

- 证书补采已有生产任务 owner、Host 通道及真实 App 复测。
- 当前打包的扫描 Node 1.0.0 仅支持草稿，`executionAvailable=false`；现有桌面扫描 owner 与独立原生服务已具备多项执行能力，但未接入当前聊天工具。优先接通桌面通道，保留独立服务与旧 Node 草稿，避免隐式迁移或覆盖历史数据。

## 第一阶段实现

扫描内置组件 1.1.1 新增 `scan_list / scan_status / scan_from_assets / scan_start / scan_pause / scan_resume`。这条通道调用当前桌面扫描 owner，独立原生服务 2.0 和旧 Node 草稿均保留，不隐式搬迁。

Host 将保存的外部项目绑定转换为桌面项目；返回统一的 Host 项目 ID，并单独说明桌面编号。仅信任桌面启动器注入的回环桥，不给模型或 Node worker 内部 bearer。读取、建草稿、执行、暂停分别使用 `investigation.read / investigation.draft.write / investigation.execute / investigation.control`；显式操作仅申请缺少的权限，已有同运行时授权复用。

原生草稿和创建回执在同一事务中提交。控制操作先保存幂等操作身份，结果未知时不自动重发；Host 证据与额度记录也保留 `outcomeUnknown`，而非误记写入完成。状态读取与历史控制回执分开。共享内部桥限制并发，扫描准入不会堵住证书状态读取或主 UI。

第一阶段回归：Host 539 通过、17 跳过；证书队列 12 通过；新通道 4 通过；原有资产草稿 6 通过、Web 启动边界 15 通过；Vue 类型与 Vite 构建通过。跳过项及这些测试都不能替代真实引擎执行验收。当前 App 安装与真实项目结果保存到本地私有报告，不将资产和配置上传仓库。

## 后续闭环，仍未整体验收

- 真实项目验证：聊天读取、库存交接、工作台同任务展示、跨项目拒绝；再检验明确授权下的原引擎执行、物理暂停和重启恢复，区分引擎准入拒绝与已执行失败。
- 新通道当前支持 Web；源码、灰盒、CI 的来源快照、工作台启动和 Agent 指令交接仍需独立验证，不能把 Web 能力外推到所有分支。
- 扫描结果查询要沿用原 owner 的证据可见性规则，保留分页和真实验证状态，避免把原始 finding 数量当成已验证漏洞数。
- 检查聊天模型与扫描模型的实际配置来源、重复入口及错误提示；不为图省事把凭证复制进模型工具参数或自动改用户连接。
- 长期性能、App 退出时控制请求的收尾、范围/权限变化与多任务并发仍需有边界的实测。第一阶段不启动全库扫描，也不消耗 Hunter 积分。

真实 App 交接发现库存镜像记录 ID 与桌面资产 ID 不一致。接口增加显式编号空间，由 Assets owner 的镜像绑定转换，再由桌面扫描 owner 复查实时项目成员；禁止以数字碰巧相同代替身份。桌面安装必须使用 prepare_desktop_agent_host 生成并验证的正式分发资源，中间 agent-first 构建不是可安装包。

同样修正证书定向补采：Assets 1.2.1 在指定 assetIds 时要求明确编号空间，省略二者仍处理整个既定范围。两条通道共用 Assets owner 的只读身份转换；跨项目、非桌面来源、缺失或非法编号均拒绝。

## 当前 App 的第一阶段实测

已安装 AgentChannels21，Assets 1.2.1、Scanning 1.1.1。正式桌面分发资源及签名均校验；通过原批准范围恢复组件升级前的读取/证书权限，以及本阶段测试的扫描读取/草稿权限，未新增扫描执行权限。

真实模型从当前项目库存定位 HTTPS 记录，成功交接为桌面原生草稿，再读原任务状态；工作台显示相同任务 ID、目标和 `draft / attempt 0`。后续读取复用权限、不重复建单。原生跨项目任务读取实际被拒绝；缺少执行权限的启动实际被拒绝。旧证书队列仍为原来的已完成结果。对完整主库逐表比较：原资产、范围、证书队列、历史扫描记录、原消息、文件授权、密钥、网络设置及 CAS 保留，本次仅新增一个原生草稿及其关联行。私有证据和一致备份保留本地，不随源码上传。

这里验证了真实读取、身份转换、交接和权限拒绝，尚未验证新扫描的网络执行、物理暂停或跨进程恢复，不能把草稿当作执行验收。

下一阶段优先修复实测发现的 UI 误诊：`draft / attempt 0` 在调查对话及任务预览中仍显示 `native_receipts_unavailable`、缺少 Native 完成回执与待核对，容易被误解为执行失败。随后验证扫描模型配置来源、启动前的可读诊断、真实执行与暂停恢复。再检查跨模块组合意图、并列否定指令与新用户首次交接授权，避免单动作优化限制复杂请求。Goal 仍为 active。

## 第二阶段实现

- 草稿诊断只在没有任何执行尝试、分支、进程、运行、清理记录、模型用量或已处理目标时显示“尚未执行，等待确认”。读取不写回完成回执，也不授予启动权限；仅改成 draft 或把次数清零不能抹去异常诊断。
- 调查对话、任务预览和原生运行页显示一致的草稿指导，隐藏尚未产生的租约就绪徽章与错误的待核对义务；保留真实执行失败、暂停中和清理问题的提示。
- Scanning 1.2.0 增加 `scan_preflight`：解析原 owner 的保存模型、任务状态和模型限制，不发送提供商/目标请求，也不冒充网络测试或完整启动准入。启动前的问题只提供读取工具。
- 真实配置审计表明当前聊天与扫描使用相同模型分类引用、服务端点及凭据。扫描的 `openai/` 前缀由原网关去除；没有复制或修改用户连接。
- 新草稿可声明 `maxModelRequests / maxModelTokens`，范围是**每个目标、每次执行**。它们收紧实际执行计划的请求、Token 和轮数上限，保留到冻结计划中；多目标各自计数，不能解释成整个项目的总限额。
- 发现旧 `maxBudgetUsd` 对普通 Web 执行未形成美元硬限额；本阶段不把金额字段包装成有效保护，也不在 Agent 新建接口提供该伪限额。只读检查明确返回 `usdLimitEnforced=false`。金额计费保护及旧 UI 的对应语义仍需继续完善；不能以请求/Token 限制宣称已实现美元费用上限。

## 当前 App 的第二阶段实测

已更新到 AgentAdmission24，Assets 1.2.1、Scanning 1.2.0，正式 Host 分发与 App 签名均校验。原草稿在调查对话和任务中心实际显示“尚未执行，等待确认”，不再误报缺少完成回执。

真实模型在当前项目查询 HTTPS 库存，创建独立单目标 quick 草稿，保存每目标每次执行 3 次模型请求、128000 Token 的限制，再读取预检及状态。实际启动原引擎后访问目标、保存侦察证据；目标没有满足继续模型调查的证据门槛，以 `recon_only` 完成，模型用量为 0。这里证明网络侦察和业务 owner 执行，不证明模型调查或漏洞验证已通过。

另建独立单目标任务，在执行中立即调用暂停，实际观察到 `pausing → paused`，原执行尝试记录线程退出，登记进程为 0。重启 App 后仍是同一暂停任务；实际聊天调用恢复，保留第 1 次暂停尝试，并创建 `execution_mode=resume` 的第 2 次尝试，随后完成侦察。任务身份、单目标范围和已保存上限保留。上限仍按每个目标、每次执行计，不能宣称跨尝试总费用预算。首次已自然完成的任务收到暂停请求时，正确保留完成态，没有伪造暂停成功。

实测还修复了两个 Host 工具分流问题：建草稿后预检误隐藏库存工具；恢复指令中的“已暂停”误选暂停工具并导致 Agent 错报未授权。修复后使用原复合请求及完全相同的恢复请求复测通过；并列禁止“不要新建、启动”、未恢复状态和多动作请求加入回归。新问题的复现记录保留在本地测试对话，不删改历史。

本阶段最终 Host 与正式分发回归 548 通过、17 跳过；新增复合与历史状态调度用例包含在内。前述 Rust、UI 和构建回归继续适用，Host 后续修正没有改动原生二进制。测试子进程采用规范临时目录 `/private/tmp`，避免 macOS `/var` 别名与文件访问范围不一致；默认临时目录下的失败也保留日志，不用真实 App 成功掩盖它。

已对一致备份与当前数据逐表比较：所有原主库业务行、原草稿、资产、范围、证书队列、原聊天消息、文件授权、密钥、网络配置及原 CAS 内容保留；新增数据逐行归属本阶段两个测试任务。仅当前项目的扫描组件增加本阶段已授权的执行与控制权限，其他项目与原授权保持。私有证明、任务记录、截图和备份只保留本机。

下一阶段仍需处理：Agent 查询真实扫描结果和停止原因的能力、证据可见性与分页；实际模型调查及其限额命中；跨证书与扫描的组合任务；完整金额计费保护与旧 UI 语义；非 Web 分支及规模/并发边界。当前单目标侦察、暂停和重启恢复通过，不能外推为整体验收。Goal 保持 active。
