# 主 Agent ↔ Nest 实时闭环：现状与下一步提案

> 状态文档，非验收。描述当前已实现的闭环、以及把"只读实时分析"推进到"可信自动纠正"所需的 prompt/编排改动与风险。live prompt（`quality-prompt.mjs` 等）本提案不直接改动，改动建议列在 §4 供评审。

## 1. 现状（已实现并真机验证）

实时事件管道与门控反应已打通（提交见 `git log`，均在 `main`、未推送）：

- **A1–A4 事件管道**：每个 worker/assignment 的阶段状态变化（不再只等 attempt 终态）带 `assignmentId/workerId/targetKey/runId` 关联、经脱敏后进入 Host 会话；`scan_results` 按 assignment 返回执行单元清单与可作 directive `threadKey` 的稳定 id。agent 因此能实时看到"哪条回复来自哪个执行单元、该用哪个 id 定向纠正"。
- **B1 门控与防失控账本**：开关 `OVIRAPTOR_AGENT_AUTOREACT`（默认关）；`decideReaction` 按事件去重、每 attempt 预算上限、超额/短时爆发熔断，全部持久化、重启不丢。
- **B2 门控反应**：新 Nest 事件（仅 worker 状态/任务结果，不含 agent 自身指令回执）触发**一次有界、按会话串行**的 agent 回合；回合有 90s 熔断，不会堵死会话。
- **当前反应是严格只读**：回合只用 `scan_status`/`scan_results` 分析，必要时给出一句话纠正建议**交人确认**，自身不发写指令。真机验证：事件→投递→反应→回合 `completed`、真实调用模型、无堵死、预算有界、脱敏生效。

**定位并修复的关键缺陷**：无头反应回合若被允许写操作，会在"请求业务授权"处死等人工应答而挂死。修复＝反应只读 + 非交互回合不阻塞授权（`service.mjs` 的 `requestAuthorization` 门控）。

## 2. 下一步目标：从"只读分析"到"可信自动纠正"

要让 agent **自动发出纠正指令**（而不仅建议），需要在不牺牲安全的前提下补齐三件事。

### 2.1 预授权的受限写作用域（避免无头授权死等）

- 自动纠正只允许一组**预先授权、范围受限**的写操作：`scan_command`(supplement)、`scan_pause`、以及针对 `threadKey` 的定向 directive。
- 这些作用域由**项目级一次性授权**开启（人工在 UI 勾选"允许本项目的自动纠正"），落在现有 grant 体系里；非交互回合据此判定 `authorizationContext`，**永不**在回合内弹人工授权。
- 未预授权 → 回退到当前的只读建议模式（已实现）。

### 2.2 更强的运行时管控（在 B1 之上）

- 现有：每 attempt 次数上限 + 短时爆发熔断 + 去重。
- 新增：**写操作单独更低的预算**（例如每 attempt 最多 1–2 次自动写）；同一 `(assignmentId, 纠正意图)` 去重，避免对同一单元反复下同类指令；任一自动写失败即对该 attempt 熔断自动写（降级回只读）。

### 2.3 回合的连贯性（editor §4 的 prompt 改动支撑）

- 自动纠正回合要能引用"这条事件属于哪个 assignment、该 assignment 已发过哪些指令、当前 `pendingCommands`"，避免重复下达或与在途指令冲突。A4 的 `assignments`/`threadKey` 与现有 `pendingCommands` 已提供数据，缺的是 prompt 明确要求模型先读后写、按 threadKey 定向。

## 3. 建议的推进顺序与验收

1. 先在**受控夹具**里实现 §2.1 的预授权判定 + §2.2 的写预算，默认关，补"关着=只读、开着=一次有界写"的测试。
2. 真机（隔离库 + 合成模型）验证：一条事件→一次定向写→被 Nest 实际消费→结果回传，且预算/熔断有界。
3. 仅当上述通过，再考虑放开给真实扫描；放开前必须覆盖：写失败降级、跨 attempt 不串、与在途指令不冲突、人工可随时收回项目授权。

## 4. 对 live prompt / 编排的建议改动（待评审，未实施）

> 以下只是建议，需人工评审后再改 `quality-prompt.mjs` / Host 轮次循环。

1. **只读先行**：自动纠正回合的系统提示明确"先 `scan_status`/`scan_results` 核对该 `threadKey` 的最新状态，再决定是否写；空读页有游标不等于无结果"。
2. **定向而非广播**：纠正指令优先用 `threadKey` 指向具体执行单元，而不是 team 广播，减少对无关单元的干扰。
3. **幂等与在途感知**：提示模型读 `pendingCommands` 与该单元已发指令，避免重复下达；同一意图已在途则不再发。
4. **写前门槛**：提示明确"仅在 scanMode/预算/范围允许且证据支持时才写；证据不足只报告，不猜测"。
5. **连贯叙述**：把"已接受/已送达/已执行/已验证"四态与自动纠正的因果串起来，面向用户解释"为什么对这个单元做了这个纠正"。

## 5. 未决风险

- 测试网此前被大量删除，"绿"不足以证明安全；§2–§3 的每步都要补精简测试并真机验证。
- 全自动写纠正本质上让模型在无人值守时改动扫描，必须预授权 + 写预算 + 可随时收回，默认保持关闭。
- 底座模型能力决定纠正质量；编排和 prompt 只能保证"安全、定向、不失控"，不能替代模型判断。
