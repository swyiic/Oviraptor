# Nest 任务、协作台、资产画像与持续学习实施合同

状态：设计与分阶段验收合同。2026-09-25。与 `NEST_STRIX_FREE_MULTI_AGENT_MASTER_PLAN.md` 同时适用；冲突时以主计划的授权、预算、证据与 Reviewer 约束为准。本文**不是已完成功能清单**。

## 0. 本轮实际状态与禁止误报

- 已有 Native-only 新任务主链、持久化 assignment/child run/mailbox、独立 Reviewer、用户指令草案与确认、任务结果详情、尝试历史、轨迹知识与聚合知识。见实施进度文档。
- 本轮任务中心加入待处理/已结束/全部分流、搜索和协作入口；对话页加入线程筛选和证据页入口。任务中心和对话页可用更新时间＋任务编号游标继续读取更早的任务，新增任务插入时不会使游标跳过旧记录。搜索只覆盖已加载页，界面明示这一点；跨全库搜索仍是后续工作。这是信息架构的第一步，不代表下述资产画像、自动补证或终身学习已经实现。
- 任务中心的单任务预览现在按“概况／执行／证据／学习”读取同一 `scan_id`：执行显示持久化 attempt，并可选某一轮读取独立的、限量脱敏的运行日志尾部、Agent mailbox 消息摘要与工具调用状态；消息与调用均可沿稳定时间＋ID 游标读取更早记录，绝不跨轮次混入。工具调用只展示 role、工具、状态、策略和请求/响应证据引用是否存在，不泄露输入和正文；“有引用”不能当成“已审核”。旧任务目录回退有明确来源标签，当前轮次的待核对事项不误贴在旧轮次。证据只给审核状态及原结果入口，学习只读取该任务的候选和知识。异步切换任务丢弃旧响应；分区读取失败不清空其他分区；不会因打开页面触发模型、目标请求或生成 Skill。协作页有本轮状态、出现过的角色、停止原因与下一步的只读上下文侧栏，不能把“出现过”解释为正在运行。当前仍不是完整任务详情：缺少按 attempt 的人工指令回看、证据 revision 逐条定位、跨全库搜索及资产画像。
- 运行诊断增加只读 `stopDiagnostic`：同一个任务/分支/目标/清理快照派生硬停、软停、能力缺失、自然结束或活动中，以及具体待核对项。只有报告中明确的 `backend_retired` 才归为能力缺失；不能解析自由文本猜 WAF/429。单任务执行与协作页可见；续跑授权和持久停机状态机仍未实现，阶段 B 只能标部分完成。
- `GET /login` 与 `GET /dashboard/analysis` 的匿名低影响连通性测试均返回 HTTP 200；8099 浏览器显示登录界面。10080 在当前浏览器环境因端口安全限制无法打开；不得绕过浏览器限制，也不得把 200 当成业务成功或授权扫描成功。
- 没有授权书、账号矩阵、动作白名单和测试时间窗时，只能做用户明确给出的入口的匿名、低影响连通性核对。不得对邻接路径、接口或账户作猜测性探测。

## 1. 页面结构：保留旧证据，不把所有功能塞进聊天

一级入口保留“概览 / 任务中心 / 协作对话 / 结果与证据 / 验证台 / 资产与知识 / 新建任务”。不要再给旧结果页加一整套平行的扫描详情；它是同一个 `scan_id` 的不同视图。

| 页面 | 唯一职责 | 现有内容处理 | 新增内容 |
| --- | --- | --- | --- |
| 概览 | 跨任务待办、最近发现、预算与保护状态 | 原机会卡与成本指标保留 | 最近失败原因、待审批计数；可直达任务 |
| 任务中心 | 创建、运行、暂停、继续、归档检索 | 原任务列表和尝试数据保留 | 待处理/已结束/全部；状态、停机原因、下一步 |
| 协作对话 | 多 Agent 已落库消息和人工指令 | 原 AgentDialog 增强，不另建伪聊天源 | 团队频道、EvidenceGap/Candidate/Assignment 线程、审批卡 |
| 任务结果 | 单任务可复现事实、覆盖缺口、发现 | 原摘要、机会、指纹、API、端点、漏洞页保留 | 顶部统一任务事实、尝试时间线、证据版本 |
| 验证台 | 人工批准的验证与对照 | 原验证/Repeater 保留 | 明示 side effect、cleanup、控制组 |
| 资产画像 | 跨任务目标的分类与技术栈 | 从已落库的目标、路径、指纹、请求证据聚合 | 类型假设、置信度、同源关系、证据云图 |
| 知识库 | 候选、聚合、批准的技能 | 原轨迹知识和技能不删 | 分层检索、退役、版本、效果反馈 |

单任务详情固定四段：`概况`（状态、scope、mode、attempt、预算、停机原因）→ `执行`（阶段、Agent、合同、工具与事件）→ `证据`（事实、反证、Reviewer、覆盖）→ `学习`（本任务候选、对历史模式的支持/反例）。每一段查询同一 `scan_id`；切换标签不创建新任务。完成任务进入已结束视图，默认只读，不自动重启；保留完整 attempts、finding revisions、artifacts、消息和用户确认审计。重试必须产生新 attempt 并提示当前 scope/身份/预算，不改写旧结论。

### 1.1 协作界面布局

```text
┌ Nest · 任务名 · target · attempt · 状态 · 预算 · 暂停/继续 ┐
│ 任务/频道                 │ 已落库协作时间线                 │ 上下文/待办 │
│ 进行中、已结束           │ 总控的派发与合并                │ scope       │
│ 团队频道                 │ Mapper 的证据与缺口              │ 身份       │
│ EvidenceGap #...         │ 授权 Agent 的质疑/对照            │ 剩余预算   │
│ Candidate #...           │ Reviewer 的反证/结论             │ 批准卡     │
│ Assignment #...          │ 人工补充及 Coordinator 回执       │ 引用证据   │
│                          ├ 指令输入 @角色（仅请求评估）──────┤            │
└──────────────────────────────────────────────────────────────┘
```

桌面三栏，窄屏改为“频道抽屉 → 消息 → 上下文抽屉”；消息正文只显示简要结论、事实引用、合同编号、状态与时间。原始响应或令牌不进聊天；点击引用跳转证据页。`正在分析`只能来自真实运行状态，不伪造输入动画。恢复使用持久序号 `after_sequence` 补拉，不因前端断线丢消息。对话只取当前线程窗口与确定性摘要，完整事件永久由 DB/留存策略管理。

### 1.2 人工消息与多 Agent 互相监督

用户的自然语言先写入原文与解析草案；解析为 `intent / refs / roles / side_effect / budget / approvals`，前端显示“可接受/需确认/拒绝”的原因。只有 Coordinator 在 Rust 侧重新核验冻结 scope、identity、capability、预算、风险、fencing 后签发合同。`@Reviewer` 是要求评估，不是让已审 revision 重复调用模型；`@授权 Agent` 不能生成缺少控制组的越权 confirmed finding。人工补充“此接口可能是退款入口”先记为假设，只有请求与响应或可信业务证据才能升为事实。

Agent 之间用带 `thread_id / revision / refs / dedup / ack` 的 machine envelope；用户只看到脱敏摘要。Proposal、Challenge、SupplyPrerequisite、Duplicate 均是建议，不是目标请求权限。相同 evidence revision 最多一轮提案和一轮质询；新事实或能力变化才重新调度。Reviewer 独立 run，不能让执行者自己确认 finding。

## 2. 停机不是“空烧门禁”：区分原因与可续动作

原 Strix 防空烧约束不能被简单删除。把限制拆成四类，分别呈现：

1. **硬安全边界**：授权 scope、WAF/429、受控写、清理、并发、身份、硬请求/Token/时间。触发即保存 checkpoint 并停止目标触达；UI 显示具体数值、消耗及重新授权/提高预算流程，不能自动绕过。
2. **软经济预算**：Token/模型次数软阈值。只有连续无新证据时才暂停/部分完成；有新事实且硬上限仍允许时继续。不得把“模型说结束”当作完成覆盖。
3. **能力缺口**：缺模型、浏览器、Analyzer 镜像、账号、控制组。标记 `partial/coverage_gap`，展示需要用户补什么、哪些事实已保留；不能显示“安全”。
4. **自然完成**：所有 obligations 已关闭，Reviewer 与 cleanup 完成，进入唯一终态。即使没有漏洞，也要展示覆盖范围和未测原因。

每个 stop reason 必须有代码、阶段、已完成目标、未完成 obligation、是否允许同任务继续、下一步、预估额外成本。`resume` 只处理未完成合同；目标调用结果不确定时不得自动重放。建议增加故障注入覆盖：模型 429、目标 429/WAF、Browser/CDP 失败、账号失效、容器失败、DB 崩溃重启，以及第 N 个请求后暂停。禁止以调高上限掩盖无限循环。

## 3. 资产画像：事实、推断和“相似接口”分开

以 normalized origin + 授权 scope 绑定 `AssetProfile`。跨任务合并需要同一租户/项目和明确归属，不能仅因 IP/框架相同就混用私有证据。

```text
AssetProfile: asset_id, project_id, origin, authorization_id, first_seen, last_seen
ObservedFact: fact_id, scan_id, attempt, URL/method, evidence_ref, observed_at, identity_class, redaction_level
TechnologyAssertion: name, version?, confidence, supporting_refs, contradicting_refs, status
SystemTypeHypothesis: portal | admin | government | commerce | logistics | unknown,
                      confidence, supporting_refs, contradicting_refs, model_version
EndpointPattern: template, methods, source_kind, last_verified, fact_refs, identity_class
KnowledgeRelation: canonical_pattern_id, support_scan_ids, counterexample_scan_ids, decay_state
```

分类是多标签且允许 unknown：登录页标题只是线索，不足以断言“政务/电商后台”。AI 只能建议分类与可能关联的框架/接口族；Rust 聚合确定性事实、去重、保留来源。相似接口存为 `hypothesis`（例如曾在同类已授权系统中见过的路径模板），**绝不**因模板存在便自动对新目标发请求；还要匹配新目标 scope、页面/JS/网络实际线索和有界信息增益。路径模板归一化去掉账号、订单号和 token；私有路径按项目隔离。

可视化首选可审计矩阵：系统类型 × 技术栈 × 证据数量/置信区间，点击格子看来源。词云只作辅助浏览，不用字号暗示风险概率；频次不等于漏洞率。每种技术栈的历史问题展示分母（经过验证的任务/目标数）、分子（Reviewer confirmed）、版本范围、时间和反例，避免“发现过一个问题”变成“所有同框架系统有漏洞”。

## 4. 学习与技能膨胀：四层而非每次扫描一个 Skill

```text
L0 原始任务事实/工具账本（不可变，隔离并脱敏）
  → L1 TaskLearningCandidate（单任务、可否决、不能全局注入）
  → L2 PatternCard（规范化方法，至少两个独立任务支持，含反例与版本）
  → L3 ApprovedSkill（人工/策略批准，容量受限，可回滚、可退役）
```

每个任务终态生成一次确定性学习报告：`尝试过的工具、输入/输出证据引用、失败/成功的假设、Reviewer 纠错、空耗与节省、未解决 gap`。模型补一份短的 `DecisionSummary`，不存链式思维或逐 token 文本；没有事实引用的建议留在 L1。对失败任务也学习“何时停止/需何能力”，但不沉淀无证据漏洞结论。

检索时先按 scope/租户与隐私级别过滤，再按系统类型/框架/任务阶段/证据质量排序，最多选择小量方法卡注入上下文；不能把整个技能库灌给 Agent。每个 PatternCard 维持 canonical key、支持任务去重、反例、可信度、最近使用、命中与真实收益。相同 scan 换模型不增加独立支持；近重复合并进同一版本；冲突进入复核而非直接覆盖。Skill 只有在可执行步骤、安全约束、停止条件和反例齐全且经审批后发布；限制活跃数量/每个分类数量，低命中或误导的版本退役。删除知识不应破坏历史任务审计；知识导出默认去标识化。

当前已有候选、聚合与转换入口，但单任务可人工转 Skill，尚无完整容量配额、版本退役、效果闭环。Qoder 不能把这节标“完成”，必须按数据库迁移、回归测试和 UI 验收逐项实现。

## 5. 与公开多 Agent 工具对照的取舍

可以借鉴公开项目的专业角色分工、工具调用可观察性、结果实时落盘、证据验证和历史复用；不移植其二进制运行时，也不把“完全自主”解释为无限权限。Oviraptor 的差异化应是用户明确授权范围、跨任务资产与知识谱系、每条目标请求可对账的预算、独立 Reviewer、可恢复/可解释的停止与人工协作。任何第三方代码/技能引入先核实许可、依赖和风险，再单独审查；不在本项目恢复 Strix 活运行时。

截至 2026-09-25 核对公开 Strix 仓库的 `strix/skills/coordination/root_agent.md` 与 `strix/skills/README.md` 后，增加以下**设计对照**，不是代码移植，也不宣称当前已实现：

- 根 Agent 不直接做目标测试，先根据 scope 分解任务，再动态派发专业 Agent；本产品已有 Coordinator 的无目标工具约束，但 Stage 10 专家的实际执行合同仍需逐一实现，不能仅显示气泡。
- 每个 attempt 维护独立的共享威胁模型：黑盒先有界侦察，白盒先读取源码边界。事实、推断和未验证假设分别标记；Agent 的纠错以带作者和证据引用的 append-only amendment 追加，不直接覆盖旧判断。跨任务只复用经治理的方法卡，不继承上一任务的目标事实或授权。
- 完成前核对同一 coverage row 的 `needs_follow_up`，由负责的 Agent 更新原行及解决依据；未闭合缺口不因最终消息“结束”而消失，也不得用重复行制造完成感。
- 每个 child assignment 有可验证的目标、输入、停止条件和去重键；只在请求/回答、冲突或关键交接时发 mailbox 消息，不为了聊天热闹制造状态消息。发现、验证、报告各自引用同一事实链。
- Skill 检索有上限且按子任务选取，不能每次扫描新造一个永久 Skill。我们的 L0→L3 晋级、退役与上下文配额仍以第 4 节的本地审批和项目隔离为准；第三方知识不能自动获得工具权限。

## 6. Qoder 严格实施顺序与验收

每一阶段先写失败测试，再实现，再跑全量质量门禁。保留原 JSON 导入和所有既有扫描证据页；不得用模拟聊天内容代替落库事件，也不得改老任务历史以“看起来成功”。

| 阶段 | 交付物 | 不可省略的验收 |
| --- | --- | --- |
| A 信息架构 | 任务中心分流、单任务详情/对话双向跳转、筛选与响应式布局 | 完成任务可从历史检索；消息和证据仍指向同一 scan/attempt；前端 build + UI 回归 |
| B 运行诊断 | 结构化 stop reason、remaining obligations、续跑策略 | 硬/软/能力/自然完成四类测试；暂停/崩溃/重入不重复目标请求 |
| C 协作闭环 | EvidenceGap 提案→有界补证合同→新证据 revision→Reviewer 重评 | 新事实缺失不重复模型；scope/身份/预算/fencing 故障全 fail-closed；多角色互相质询有事件 |
| D 资产画像 | profile、技术断言、系统类型假设、端点模板及证据 UI | 同项目/跨项目隔离；未知类型不强分类；未验证路径不会触达；删除/脱敏/来源可追溯 |
| E 学习治理 | L0–L3、去重版本、检索/退役、效果反馈 | 同 scan 多模型不加支持；反例阻止错误推广；配额/回滚；知识不泄露账号和私有 URL |
| F 真实验收 | 授权书、账号矩阵、两入口的任务与报告 | 记录 scope、时间窗、动作白名单、原始 stop code、请求计数、最终覆盖缺口；不能用 HTTP 200 代替 |

最终门禁：Rust 全目标测试、Clippy `-D warnings`、fmt、前端 build、Native loopback E2E、`git diff --check`、旧 JSON 回放和真实目标的授权验收矩阵。每个阶段在进度文档写“已实现/仅本地通过/需实测”，附测试命令及输出；一阶段失败不继续报下一阶段完成。

## 7. 真实 URL 联调输入合同

针对用户给定的 `http://222.92.38.52:8099/login` 和 `http://222.92.38.52:10080/dashboard/analysis`，在正式扫描前需登记：授权主体与有效期、是否允许该 IP 的两个端口、允许的路径/动作/方法、时间窗、请求率与总数、生产/测试环境标记、是否允许登录及用户提供的测试身份、是否允许创建/修改/上传及清理方式、遇到 WAF/429 的处理。账号/密码从专用身份通道录入，不进入普通聊天或日志。先匿名只读，随后单身份，最后在明确控制组存在时做多身份验证。只要缺其中关键条件，系统应输出明确待补材料，保持已采集的证据，不擅自推进。
