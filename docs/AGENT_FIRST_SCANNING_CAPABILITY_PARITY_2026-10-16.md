# Scanning native application: capability and remaining migration contract

Date: 2026-10-16. Phase 1 is committed in `e80c501`; its 214 focused native cases passed. Phase 2 below is implemented and source-frozen for compilation. No phase-2 runtime result is implied by this document. The full desktop Scanning application continues to use its original handlers.

The new native package is not full Scanning parity yet. Its real execution path is the original Web runtime, with a service-owned SQLite database and original authority checks. Source/Greybox/CI, full results, identity setup, financial operator recovery and the existing workbench UI still need explicit adapters and acceptance.

## Executable boundary now implemented

`oviraptor-scan-service` dispatches the original private guardian before any public protocol. The version-2 public SDK starts an application only after package/manifest validation and a valid lifecycle start. `scanning/service_bootstrap.rs::native_application` opens the real service; `native_service_application.rs` validates the typed SDK host context and maps the declared permission to a narrower internal scope. Model tools cannot pass a project ID, filesystem root, model credential, authority receipt, or replacement executable.

The physical compatibility schema is explicitly private to this application. The Host does not query `sentinel_*`, `agent_*`, Assets, billing, or administrator tables. Its broader desktop-era schema remains transitional; this is not claimed to be a domain-only database initializer. Assets installation and Assets data are not required for explicit-URL scans.

The durable service action journal is an outer transport journal. It does not replace original execution receipts. It claims `(project,operationId,verb,task,args hash,grant revision)` before dispatch. Repeated claims return the original disposition; prepared/uncertain work is never automatically rerun. Failed original startup can be classified rejected only when the complete original scan/attempt/target snapshot is unchanged. Otherwise the service retains uncertainty.

The original draft-only custom bootstrap protocol remains draft-only. It cannot supply execution permissions. The retained Node schema-1 draft package is unchanged and cannot launch native code. The new package declares schema 2/native runtime explicitly.

## Next source/workbench adapter: narrow implementation seams

The next change should reuse `start_workbench_scan_with_environment`, not create another Source executor. It already accepts the trusted service environment and takes owned DB/work roots. The unresolved parts are service-owned source provisioning and atomic task membership, not an AppHandle dependency in its launch.

1. Add operator-only bounded source provisioning into the application's private managed source store. Model tools receive an opaque source reference with immutable digest and project binding, never a raw path. Directory/file names, byte/file ceilings, symlinks and incomplete uploads must fail closed. A model call cannot import an arbitrary desktop path. This data transfer is not a Source execution receipt.
2. Add the same narrow owner-transaction publication seam already used for Web drafts to `publish_workbench_start`. A desktop wrapper supplies a no-op. The service supplies its operation/task binding inside the **existing** original publication transaction, before commit/spawn. Preserve the original scan-ID generation, all validation/SQL, Source scope receipts, retry basis, quiescence guards and Source/Web spawn reconciliation. Claim a durable operation before calling the owner; a failure after dispatch remains uncertain. Do not insert membership after the method returns, because a lost return could strand a running task without its own ledger.
3. Accept a closed typed workbench input containing source reference, exact URLs, policy and selections. The service injects host project identity and resolves the source reference; trusted roots/model keys remain out of tool arguments. Separate first creation from any explicit human approval required by the unchanged original contract. Retry must reuse original `load_workbench_retry_input` and preserve even an empty historical skill selection.
4. Reuse the original Source/Greybox/CI execution and result readers. Source-only construction must not resolve browser resources. Existing `source_model_cost_admission` restrictions are preserved, including any currently unavailable capped-cost mode. Unsupported paid/ambiguous continuation stays refused; this migration does not issue financial authority.
5. Add read adapters first for actual branch status, audited Source findings, attempt timeline and bounded runner/SDK/process logs; then operator actions for identities, tools, directives and financial recovery. Domain readers run against the same service custody guard; every task/attempt access checks own instance/project membership before original readers.

Required acceptance uses the actual version-2 package and built native binary: real SQLite/work directories, fixture-only model/target transports, zero paid/external calls, original task/attempt/lease/budget identity unchanged after page/Chat detach, busy disable/uninstall refusal, reattach via saved task list, no duplicate operation execution, stale grant/project denial, schema/custody replacement refusal, guardian reentry and exact original financial rejection. Controller unit tests or a busy-label fixture cannot establish this acceptance.

Current native upgrade candidates that copy an existing engine DB to another inode/path must be refused. No marker/HMAC rewrite makes old births portable. Old desktop tasks stay in their original desktop path/executable. A later explicit read-only history export plus genuinely new task birth is a separate contract from execution adoption.

Expected additional work after phase-2 compile and actual package tests: Source provisioning/publication and focused tests about 3–6 hours; detailed read/result/log adapters about 2–4 hours; operator identities/approvals/directives/financial recovery and full UI parity about 1–2 working days. These estimates are not acceptance results. The first explicit-URL chain is useful progress, not permission to declare the remaining 113-call desktop surface migrated.
