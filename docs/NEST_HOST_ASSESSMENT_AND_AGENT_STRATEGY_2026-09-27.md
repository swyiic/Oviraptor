# 独立主机安全评估与按需多 Agent 实施设计

更新日期：2026-09-28（本地时间）。状态：产品与实施合同，**不是已交付功能清单**。§15 为少量双平台设备的首版范围、按需协作及验收补充；§16 规定跨模块组合，§17 补齐当前源码人工引导缺口的实施要求。

阅读顺序：产品负责人先读 §1–3、§15.1–15.4 和 §16；实施者以 Master Plan 为总约束，再按 §15.7 的工作包顺序落实，并逐项验收 §16.4、§17。自动化结果及当前阻塞以 `NEST_CHAT_ASYNC_AUDIT_2026-09-26.md`、`NEST_IMPLEMENTATION_PROGRESS_2026-09-23.md` 的最新记录为准，不从本设计稿推断功能已可用。

少量 Windows/Linux 混合设备如何排期、分配执行资源和选择协作模式，另见 §18；该节仍为待实现要求，不新增主机执行授权。

### 本轮产品决策摘要（供排期确认）

- **独立入口**：Web 扫描、源码扫描、灰盒扫描、CI/CD、主机安全评估五类工作入口平级；Windows/Linux 是主机模块内的平台选项。主机评估不隐藏在 Web 的高级选项里。
- **先区分设备用途**：如果部门的 Windows/Linux 只是用来运行浏览器和扫描工具，它们属于执行节点，放在环境管理中；只有检查这些设备自身的配置、账户、补丁与服务时，才创建主机安全评估任务。不能因新增执行节点而自动登记为获准评估的目标。
- **首批用户故事**：部门 Windows 工作站自查、Linux 工具机自查、整改后再次采集比较。先做人工采集包导入，不以常驻 Agent、远程连接或 Kali 为前置条件。
- **不争抢主线排期**：先使现有扫描可靠完成，再交付源码按需模式及灰盒/CI 组合，最后做主机离线 MVP。未完成的入口隐藏或标为规划中。
- **源码默认不组建团队**：目标产品的日常检查以确定性工具为主，按需单分析者解释；复杂问题才进入专家协作。当前源码模型执行链仍有多个角色，这项默认策略需要真实后端改造和零模型调用验收，不能仅改页面。
- **协作共享证据，不共享权限**：联合评估关联独立任务；聊天按具体任务路由。新增在线目标、仓库或主机操作需要对应合同，不能由其他任务的 Agent 代为授权。
- **交付证据**：Qoder 按 §15.7 分包执行；每包提交实现差距、代码路径、可复现测试、已知限制。本文的待验收框不能仅凭代码存在或前端演示打勾。

## 1. 决策与优先级

1. 新功能命名「主机安全评估」，与 Web 扫描、源码扫描、灰盒扫描、CI/CD 平级。用户所称“灰度扫描”在本文按现有 Greybox／灰盒理解；灰度发布不是本模块概念。
2. Linux、Windows 是主机任务的目标平台，不是两个重复产品，也不是 Web 任务里的提权开关。
3. 先完善现有 Web、源码、灰盒、CI/CD 的正确性、恢复、证据与 UI，再交付主机只读 MVP；远程执行后置。本轮不新增可执行 Host Agent。
4. 平级导航不等于相同实现优先级。主机未交付时仅可显示「规划中」或隐藏入口，不提供会成功返回的假启动按钮。
5. 多 Agent 是按证据需求启用的执行策略，不是所有扫描必须有的形式。工具进程、线程和聊天角色数量都不等于独立 Agent 数。
6. 保留现有 JSON 原文和只读历史兼容；历史报告、采集包中的角色名、授权字段不能恢复执行权限或成为本次独立审查证明。

本文件扩展 Master Plan §6.4 的未来平台规划，不放宽现有 `web_only`。发生冲突时，授权、历史只读、真实回执和独立审查约束不降低；旧文档的“Windows 不支持”按“当前未支持，未来独立阶段”理解。

## 2. 适合少量机器的场景

先区分三种机器：操作 Oviraptor 的控制端、运行工具的执行节点、接受评估的目标主机。同一物理机即使承担多种职责，也不能共享权限合同。安全部门的一台 Linux 工具机，并不代表已授权检查所有目标 Linux。

### 2.1 第一阶段：只读采集包导入

由管理员在明确授权的 Windows/Linux 上手动运行已审阅、带版本和摘要的采集器，查看采集范围后导出文件；Oviraptor 离线导入、规则评估、AI 解释、独立复核与生成整改清单。不要求常驻后台服务、域控、Kali 或一机一个 LLM Agent。

初期可以只有一台 Linux 与一台 Windows 测试机或可回滚虚拟机。它们足以验证明确列出的基础场景，不代表覆盖全部发行版、Windows 版本和企业域策略。没有真实 Windows 环境时，只能验收解析夹具，不能宣称 Windows 采集器已验收。

| 场景 | 采集内容 | 输出和约束 |
| --- | --- | --- |
| 资产盘点 | OS/版本、安装软件、服务、监听端口的本地元数据 | 带采集时间的快照；不据此扫描其他网络地址 |
| 基线核查 | 防火墙、审计、登录策略和选定服务配置 | 每项通过／不通过／未知／不适用；规则版本可追溯 |
| 补丁与组件风险 | 软件包或更新记录、产品版本、来源 | 候选风险及适用性；不能仅凭版本字符串确认漏洞，保留回补补丁等不确定性 |
| 账户权限检查 | 用户/组/权限配置的必要元数据 | 敏感标识脱敏，不采集密码、哈希、令牌或私钥 |
| 整改复测 | 同一资产的新快照与此前证据 | 基于稳定身份、相同规则与时间对比；“本次未采到”不是“已修复” |

Linux 规则首批范围可选择 SSH 配置、sudo 策略元数据、服务与防火墙、文件权限元数据。Windows 首批范围可选择本地账户策略、审计、防火墙、防护状态和服务配置。**这些是待开发范围，不是当前工具支持声明**。

读取过程也可能消耗 CPU、磁盘或产生系统日志；“只读”不等于无影响。所有采集器必须有超时、输出上限、并发限制和敏感字段排除清单。

### 2.2 后续：受限远程只读评估

仅在离线 MVP 验收后选型。Linux 研究受限 SSH 账户和固定采集程序；Windows 研究受限远程管理 endpoint（例如 WinRM/JEA 方向）。实现前必须核对官方版本、认证、加密和权限文档，并形成独立安全评审，本文不承诺任意版本兼容。

禁止自动打开目标远程管理服务、自动扩大防火墙、默认使用 root/管理员、忽略服务器身份校验。凭据存于秘密存储，任务仅持句柄；不进入模型、聊天、报告或知识库。若环境不具备安全连接条件，继续使用人工采集，不强制用户部署远程 Agent。

### 2.3 不属于首版的范围

爆破、凭据提取、提权、持久化、横向移动、任意远程 shell、自动修复、域级评估均不进入 MVP。未来若有合法业务需求，另立动作合同、审批与验收；不能从“主机评估已开启”推导许可。

“批准复测”只许可冻结列表中的检查；修改配置、安装补丁、重启服务属于独立变更流程，必须有影响说明、备份／回滚和人工批准。

## 3. 五类功能如何组合 Agent

以下为目标策略，不表示当前已支持自动选档。Coordinator 是编排职责，不要求每个调度 tick 都请求模型；解析、规则匹配、预算、授权与状态迁移优先使用确定性代码。

| 功能 | 默认执行方式 | 何时增加专家 | 独立复核 |
| --- | --- | --- | --- |
| Web | 编排器＋按需侦察/浏览器/验证职责 | 登录身份差异、业务流程、不同证据分支确有需要时 | 正式确认由独立 Reviewer 核验执行证据 |
| 源码 | 固定工具流水线；AI 分析按选定档位 | 跨模块数据流、跨服务、复杂鉴权、规则无法解释的候选 | AI 确认仍需独立 Reviewer；工具输出不自动升级 |
| 灰盒 | 已授权源码分析＋已授权 Web 验证＋关联分析 | 有明确路由/版本/部署映射和待验证假设时 | 区分代码风险、运行可达性、实际验证；不得互相冒充 |
| CI/CD | 冻结 diff/材料/规则/策略的确定性流水线 | 高风险变更或候选需要解释/复核时，使用有界任务 | 根据冻结策略判定；AI 缺席或超时不能静默算通过 |
| 主机 | 采集 executor＋对应 OS 规则分析；按需 AI | 非标准配置或关联证据不足时 | 独立 Reviewer 可读证据，不取得目标执行权限 |

### 3.1 源码不必默认“群聊式扫描”

规划三档，用户可见且创建 attempt 时冻结：

- **工具检查**：解析、SAST/SCA/秘密规则等已安装并获准的工具；可完全不调用模型。发现标记 `tool_reported`／待审查。规则门禁可以在明确冻结的工具策略下独立使用，但不得标记“AI 已确认”或“完整审查通过”。工具清单以实际能力为准，不为缺失工具伪造结果。
- **辅助分析**：在工具结果上启用一名分析职责；有需正式确认的候选时启用独立 Reviewer。适合日常小项目和有限 diff。
- **深度协作**：按问题分配 RepoMapper、SourceAnalyst 或专业子任务，加独立 Reviewer；适合复杂跨服务问题。每个新增 assignment 必须有独立问题、输入范围、预算与完成条件。

不能简单按代码行数选档。参考语言/模块边界、鉴权与危险 API 变更、历史风险、资料完整性、候选数量及预算。用户可预选；运行中建议升档必须展示原因、增量预算和范围变化，获得需要的批准后新建合同版本／新 attempt，不暗改冻结合同。

**当前代码差异（2026-09-28 续报）**：`native_source_coordinator.rs` 的本地新任务注册入口已从 v3 更新为 v4，旧根保持原冻结版本；这仍不是上述自适应策略。v4 已有独立覆盖 Reviewer 和不可变覆盖裁决模块；`source_review_projection.rs` 已统一读取候选裁决与实际覆盖裁决，CI、findings 及其导出路径已接入，`SourceReviewEvidence.vue` 也已有展示与校验。此前“消费链仅使用覆盖准备结果”及“默认仍为 v3”属于更早快照，不再作为当前缺口。默认入口升级的红绿测试、后续回归状态和限制以 `NEST_SOURCE_COVERAGE_REVIEW_EXECUTION_AUDIT.md` 为准；代码接入和注册测试不等于产品或安装包验收。`independentCandidateReviewCompleted` 与总体 `independentReviewCompleted` 必须继续分开。Qoder 必须新增并测试 profile 合同，不能仅隐藏角色 UI 就声称“工具模式”，也不能删掉现有独立裁决链来节省调用。源码模式的“工具检查/辅助/深度”与内部合同版本 v1–v4 不是同一个维度，禁止按数字直接映射。

### 3.2 防止多 Agent 空转

- 每个角色有任务切片、证据引用、输入/输出上限、调用预算、期限与退出条件；没有可执行的新假设不重复开会。
- 同一证据问题去重；争议不能无限互评，进入有限追加取证或“证据不足”终态。
- Reviewer 不复用提出该候选的身份/assignment，不自动接受其结论；可用相同模型，但上下文、身份、权限和回执独立。相同模型不代表独立模型能力，报告需如实说明。
- 模型并发、工具并发、浏览器进程、主机连接分别限流。初始产品策略建议模型最多 2 个并发、单目标采集 1 个；这是待基准测试的默认值，不是当前已实现的硬上限。
- 总预算耗尽需落库暂停/部分完成原因；缺单项工具只影响相关覆盖，不让整任务被笼统“门禁失败”吞掉。

## 4. 主机任务与 Web 任务严格分开

Web 发现疑似主机问题时，仅保存 `host_boundary_candidate`，可生成主机任务草案。不得在原 Web attempt 内批准 SSH、OS 命令或借 HTTP 参数执行命令。

创建主机任务必须重新选择目标、平台、授权与动作；目标来自人工确认的资产，不把网页内容、DNS/IP 推断或模型建议直接当权限。来自 Web 的任务保存父任务和证据关联；独立盘点任务允许无父任务。

父 Web 任务可在自身授权内继续或正常结案，显示“主机部分未验证”。主机结果作为关联任务展示，不改写原 Web 历史，也不合并预算与凭据。

### 4.1 建议冻结合同（新设计，未实现）

应至少包含：`taskId/attempt/rootRunId`、平台与支持版本、目标稳定 ID、连接地址和服务端身份绑定、授权引用/审批人/有效期、采集 profile 与摘要、允许操作 ID、credential handle、执行节点 ID、工具包 digest、规则版本、资源与时间预算、数据保留策略、停止/清理条件、可选父任务/证据引用。

离线导入合同不包含连接凭据，也不签发远程 capability。对历史采集只能证明导入来源和内容完整性，不能倒推采集当时具备实时授权。

### 4.2 审批与门禁位置

| 控制类型 | 执行位置 | 命中后的行为 |
| --- | --- | --- |
| 目标、动作、凭据、期限、撤权 | 后端合同与 Broker，每次派发前校验 | 拒绝相关动作；全局撤权停止新派发 |
| CPU/内存/进程/输出/时长 | 执行器与可用 OS 隔离机制 | 限流、取消、回收并保存部分结果 |
| 单规则无权限、缺工具、无证据 | 子任务与覆盖账本 | 标记未知/未覆盖，允许其他合法工作继续 |
| 结论质量、相互矛盾 | Reviewer 与裁决层 | 追加有界取证或不确认；不能授予权限 |
| 未知远端执行结果 | 恢复与核对层 | 不盲目重发；记录待核对并给操作者明确处置入口 |

移除不合理的“固定步数一到全部失败”前，先写出真实停止原因分类和回归。Agent 监督补充质量控制，不能替代授权、安全停止或资源限制。预算调整只走显式合同流程。

## 5. 采集包、工具供应、沙箱与数据可信性

### 5.1 包格式和导入

规划独立版本化格式（例如 `oviraptor-host-assessment-v1`，最终名称经合同评审确定）：manifest、采集器/规则版本、平台、资产标识、开始结束时间、操作清单、逐项状态、证据文件大小与 hash、脱敏策略和可选受信签名。

- 文件 hash 只能证明对应字节完整性，不能证明机器身份或采集内容真实。签名必须绑定经配置的受信身份；自签/未知签名不能升级可信等级。
- 缺字段、超限、压缩炸弹、路径穿越、符号链接、摘要不匹配先拒绝；先暂存校验后原子发布，不部分写正式结果。
- 未签名历史包可按策略只读导入，明确标记 `historical_external`、未验证来源；即使 JSON 写着 confirmed/admin/authorized，也没有执行或审查权。
- 原文与脱敏展示分层保存；原文若含意外秘密，限制访问并阻止模型读取，不把“保留原文”理解为允许公开传播。
- 相同字节重复导入幂等；不同采集轮次不合并，冲突并存，不覆盖既有快照；删除资产/任务后重导入不复活正式任务。
- 离线采集时间由目标声明，另记服务端导入时间和可验证的签署时间；有时钟偏差时禁止强行按目标时间推断整改顺序。

### 5.2 供应策略

工具能力包在任务开始前安装、校验、锁定版本和摘要；记录许可证与来源，提供离线准备说明。运行中 Agent 不自行联网拉脚本或安装工具。

不够工具时显示“缺少能力/影响范围/准备方法”，可继续其他检查。不可静默下载，不可将缺工具解释为安全。采集包、依赖供应与更新程序都要独立安全审查。

### 5.3 环境生命周期

复用只读镜像/工具缓存，任务使用隔离可写工作区；不把前次凭据、目标文件、浏览器会话或进程带入下次任务。一个任务可共享受控证据存储，不共享任意可写 shell。不同目标和不同权限至少隔离 credential、process、lease、budget 与输出命名空间。

离线评估第一阶段无需为每个 Agent 启动 VM；解析器与规则仍须有资源限制。Windows 采集使用已授权 Windows 环境验证，不假设 Linux 容器能替代。沙箱冷启动/热启动、内存、CPU、回收时间必须实测后写入支持矩阵，不预先承诺秒数。`nice` 只调整优先级，不作为硬 CPU 限制验收。

## 6. UI 与信息组织

### 6.1 入口和任务中心

任务创建页按 Web／源码／灰盒／CI/CD／主机安全评估展示类型。现有任务中心统一支持类型、资产、状态、负责人、风险、时间和归档筛选；不再为每种任务维护一套互不相通的历史列表。

主机创建向导依次：选择离线导入或已验收连接模式 → 选择平台/资产 → 选择采集范围和规则 → 确认授权与数据策略 → 查看能力/预算 → 创建任务。尚未交付的连接模式禁用并解释，不将其伪装成可用选项。

### 6.2 主机任务详情

复用公共详情框架，但使用主机自己的内容：

- 概览：资产、采集时间/导入时间、可信等级、支持平台、结论范围、授权有效期与覆盖缺口。
- 检查项：通过/不通过/未知/不适用分开计数；按 OS、控制类别和规则版本筛选。
- 发现与证据：实际值、期望值、来源/摘要、规则理由、Reviewer 裁决、误报说明；默认不显示敏感原文。
- 协作：真实 Agent 事件、人工消息和处理回执；无 AI 的工具任务显示工具事件，不伪造多人对话。
- 执行与资源：工具版本、逐项耗时、退出状态、资源峰值、停止原因和日志上限。
- 复测与报告：对比两次资产快照，标记新增/仍存在/已验证修复/本次未知；固定报告版本和关联任务。

终态任务只读保存并可归档；“重新评估”创建新 attempt/任务并关联，不抹旧证据。归档不是删除，数据保留和删除策略另列。

### 6.3 聊天与人工引导

消息显示“收到 → 解释为提案 → 待确认/拒绝/已排队 → 执行中 → 已生效/失败/过期”，不能收到即宣称执行。用户说“重点看看防火墙”可调整合法子任务优先级；说“修复配置”只产生变更草案，不能直接执行。

默认显示进展摘要、证据差异、待办与需要人工决策的事项；内部重复 ACK 和工具细节折叠。Agent 只输出可审计理由与证据摘要，不要求保存或展示模型隐含思维链。源码轻量模式没有必要显示持续滚动的多人群聊。

## 7. 资产与学习复用

资产记录必须区分“观察到”“AI 推断”“人工确认”，保存证据、时间、置信与版本。网站业务类型、框架与主机 OS 分不同维度；发现某路径不能推断其他资产必然存在同一接口，更不能据此扩大探测范围。

每次任务沉淀两类资料：资产私有事实（限项目权限）与可复用知识候选（脱敏规则、分析模式、工具兼容性、误报条件、验证案例）。默认不跨项目共享内部路径、代码、主机名或业务数据。

不把每个任务总结自动变成 skill。知识流程为：候选 → 去重/合并 → 来源与安全审查 → 固定样例评测 → 批准发布 → 版本化使用 → 复测/降级/弃用。记录检索、实际引用、验证成功和误报；这些指标帮助评估，不能仅因“被用过很多次”自动晋升。

“Agent 成长”指受控知识/规则/工具策略改进，不是每轮自动修改模型权重或赋予更多权限。保留固定评测集与回滚版本；新知识必须证明适用条件和收益，避免技能无限膨胀。任务中的网页、源码注释与采集内容均按不可信数据处理，不能成为新的系统指令。

仅有明确用户需求和单独验收时建设；与只读评估分合同、分角色、分入口，不纳入本次承诺。

## 11. 少量机器的具体使用流程

以下为产品验收场景，不是已完成的实机测试。产品不以机器数量决定必须安装多少 Agent；执行采集的程序与负责分析的 AI 是两种职责。

### 11.1 安全部门自有 Windows 工作站与 Linux 工具机

1. 在资产中心手动登记两台设备及其用途、负责人、平台、授权引用；不自动扫描整段内网。
2. 新建「主机安全评估」批次，选择「工作站基础检查」与「Linux 工具机基础检查」。一个批次包含两项独立资产评估，每项单独记录采集权限、状态与证据；一项失败不能抹掉另一项结果。
3. 产品展示版本锁定的采集包、采集字段、排除字段、运行权限与预计影响。管理员确认后自行运行；一般权限无法读取的项目记为未知，不自动提权。
4. 导入两个采集包，先校验再执行对应平台规则；检查页面可不启用任何模型。
5. 用户按需点击「解释选中问题」产生有界 AI 分析；需要 AI 正式确认时再创建独立 Reviewer。规则判定、AI 解释和复核裁决分列，不能覆盖彼此。
6. 负责人在产品外按变更流程整改；再次采集并新建复测。稳定资产身份、规则和证据可比时才能判定变化，否则展示不可比较原因。

首版可支持手工批次，不引入定时后台采集、终端管控或完整企业终端运维平台。部门机器少时，先把检查、整改、复测做可靠，远程连接不是必选前提。

### 11.2 已授权业务服务器上线前检查

在明确许可的服务器上使用「服务器基础检查」和已支持的服务配置 profile，输出基线差距及修复建议。与对应 Web 资产人工关联，可并排查看应用问题与主机配置问题，但不能仅因同 IP 就合并为同一资产或继承权限。

若服务器不能安装软件或不能出网，使用事先准备并经过验证的离线采集包；目标环境不满足采集条件时停止该检查并给出缺口，不临时从互联网拉脚本。首版不以服务可用性测试、漏洞利用或配置修改证明风险。

### 11.3 Web 或灰盒任务发现主机相关线索

Web 任务记录线索与证据，用户点击「创建关联主机评估」后得到未批准的任务草案。用户重新确认资产、操作范围与授权，再选择离线采集或未来已验收的远程模式。原 Web 任务继续自身合法工作，不等主机草案批准才能结案。

主机任务完成后在两个详情页互相链接。所谓“组合使用”是任务与证据关联，不是允许 Web Agent 自动登录服务器。

## 12. 共用协作底座，而不是五套 Agent 系统

### 12.1 逻辑模块边界

初期采用同一产品内的逻辑模块，不要求拆成五个独立服务或部署五套模型。复用已有任务、attempt、assignment、child-run、mailbox、证据存储、预算、秘密存储、聊天与归档能力；复用前必须核实接口满足隔离要求。平台采集器、规则适配器和执行动作合同独立，不复制整套编排器。

建议新增合同表达以下独立维度，具体字段名由现有 schema 兼容性评审确定，禁止直接把示例当成已经存在的字段：

- 评估类型：Web／source／greybox／host，决定允许输入及动作。
- 触发方式：人工／CI，决定触发上下文；CI/CD 在 UI 上保留平级入口，但后端可调用同一源码或 Web 能力，不复制扫描逻辑。
- 分析档位：工具检查／辅助分析／深度协作，决定是否及如何签发模型 assignment。
- 采集方式：已有材料／本地受控工具／未来远程采集，与分析档位分开。
- 目标平台：仅对需要平台信息的任务冻结；Windows/Linux 不成为全局互斥运行模式。

例如 CI 源码增量检查可以是“source＋CI＋工具检查”，人工复杂代码审查可以是“source＋人工＋深度协作”，主机包解释可以是“host＋人工＋辅助分析＋已有材料”。实现须验证合法组合；不能用改一个类型字段跨越执行面。

### 12.2 Agent 启用规则

工具能给出可重复判定时先跑工具；需要上下文解释时启用分析者；存在需要独立核验的 AI 结论时才签发 Reviewer。Reviewer 不等于再跑一遍任意扫描：输入限于候选、证据与明确的审查问题。总体覆盖审查与候选复核是两项合同，前者完成也不代表缺工具、无权限等缺口已消失。

深度协作中的专家可以按需顺序工作，不要求同时驻留。由确定性调度器先检查是否已有相同问题的有效结论、是否有新增证据、是否剩余预算，再决定是否允许新 assignment；不要让模型通过聊天自行无限拉人。

不存在“选了深度协作就必须有更多发现”的验收条件。验收重点是输入范围可追溯、任务分工真实、没有重复开销、结论证据充分、资源和失败行为可解释。

### 12.3 人工消息如何作用于不同任务

- 「重点看登录模块」：只对当前任务内已授权材料/路由提出重排建议，落库后给出实际处理回执。
- 「请另一个 Agent 复核这个结论」：建立明确候选的复核提案，检查身份独立性、材料和预算；缺证据时不能假装已复核。
- 「从这段代码验证线上接口」：生成关联 Web／灰盒任务草案，要求目标及线上访问授权，不直接给源码任务发网络权限。
- 「看看这台服务器配置」：生成独立主机草案，不升级当前 Web capability。
- 「以后都这么检查」：生成脱敏知识或检查模板候选，经过审查后再发布，不把一句聊天变成永久规则。

聊天面板共享展示组件，但线程绑定任务、attempt 与项目权限。跨任务消息仅传递显式引用且经授权过滤的摘要；归档线程不会因新任务启动而恢复派发。

## 13. Qoder 执行补充：交付边界与停止线

不要把本文件所有阶段一次性并入当前运行时。先提交现状差距与依赖清单，继续完成 §8 的 P0；P1 的源码 profile 合同验收后，再逐个接入其他功能。主机 P2 单独作为后续里程碑。

按以下工作包拆分提交与验收，每包必须列出迁移策略、失败行为、回归结果及尚未支持项：

1. **模式合同与兼容**：为新任务冻结分析档位；保留旧 attempt 的原始模式/预算/角色约束。工具档真实模型调用计数为零，且不会因页面打开或报告导出自动调用模型。
2. **源码消费链**：调度、完成判定、CI 策略、导出、历史回读及 UI 一起适配模式；不能只修改创建页。相同冻结输入与规则下，工具发现不因是否开聊天而丢失；AI 新结论另留来源。
3. **协作 UI**：工具档默认显示检查进度与日志，辅助档显示分析/复核卡片，深度档显示真实任务协作时间线；人工输入共用提案及回执机制。分别验收取消、重入、跨任务切换与归档。
4. **主机离线合同**：只在 P2 开始后新增包格式和平台支持矩阵。采集器不能借用 Web executor；包导入不能恢复执行权限。批次汇总与单资产记录分离，明确失败和未知分母。
5. **双平台试点**：分别完成真实 Windows 与 Linux 的采集、导入、权限不足、超时、脱敏、整改复测与资源回收测试。未完成的平台显式标记未验收，不能用解析测试替代实机采集。
6. **远程功能评审**：仅在手工采集确有维护负担时进入 P3；新的连接方式、凭据或执行权限须独立批准，不作为 P2 隐含依赖。

主机模块可见性、离线导入能力、远程采集能力分开控制；默认不得启用尚未验收的远程能力。服务端是开关的执行依据，前端禁用按钮不是权限控制。未来关闭远程能力时应拒绝新派发，对在途动作进行有界停止/结果核对，仍允许按数据权限查看既有报告。

本次补充只调整设计文档：没有新增模式合同、主机导入器、采集器、远程连接器或 UI 功能；不得将这些工作包勾选为已实现。

## 14. 本次产品决策细化：默认体验与交付判定

### 14.1 首屏按工作目的组织，不按 Agent 数量组织

五个平级业务入口为 Web 扫描、源码扫描、灰盒扫描、CI/CD、主机安全评估。任务中心、资产中心、知识库是共用入口，不归属于任一种扫描。CI/CD 是独立业务入口，但复用底层扫描能力与证据合同。

创建页先问“检查什么”，再问“需要多深”：

| 用户选择 | 建议默认体验（待实现） | 用户明确选择后才出现 |
| --- | --- | --- |
| Web | 授权范围、登录身份、目标保护、预算；按需分工 | 专家配置与深度协作设置 |
| 源码 | 本地快照/差异范围、可用工具、工具检查 | AI 辅助或深度协作及预计额外调用 |
| 灰盒 | 代码快照与已授权部署的绑定、两侧覆盖范围 | 基于候选的有界在线验证 |
| CI/CD | 仓库/触发事件、冻结检查策略、结果输出 | 有界 AI 分析；禁止默认交互等待人工聊天 |
| 主机安全评估 | 资产、Windows/Linux、离线采集包、规则范围 | 已单独验收并获准的远程采集 |

默认值是新任务产品策略，不能重新解释旧任务的冻结合同。推荐选档依据需要显示给用户，不保证任何档位覆盖全部问题。

详情页保持同一骨架：概览、检查/发现、证据、协作、执行记录、报告/复测。工具模式的协作区折叠并明确“未启用 AI”；辅助模式突出问题卡片与复核；深度模式才展开团队时间线。不要为填满聊天框创造消息。用户随时能查看真实工具进度、部分结果和缺口，无须打开聊天才能获知任务状态。

### 14.2 三个端到端组合验收故事

1. **日常源码检查**：用户选择一个 diff 和工具档；后端冻结输入及工具规则，完成扫描并导出工具结论，模型调用为零。用户之后要求解释某条发现，应建立关联分析记录或新的受控 attempt，引用原证据；不得在已归档的工具任务里偷偷调用模型或改写其结果。
2. **复杂鉴权问题**：用户明确选择深度源码分析；专家分别检查入口、权限判断和跨模块数据流，独立 Reviewer 核查证据。若还需在线证明，只创建待确认的 Web/灰盒草案。用户确认目标、身份和预算后才能执行；最终报告区分代码候选、运行时证据与未覆盖项。
3. **部门两台机器自查**：用户建立一个 Windows/Linux 批次，各自人工采集并导入。Linux 包成功、Windows 包权限不足时，批次展示逐资产状态，不能整体显示“全部安全”。可以只针对未知项请求 AI 解释；AI 不能根据推测把未知变成通过。整改后分别导入新快照，保留旧报告与比较依据。

以上故事先用本地材料、模拟执行器和回归夹具覆盖合同，再对明确支持的真实平台验收。不得把目标 URL 可访问当作目标主机已获准评估的依据。

### 14.3 Qoder 执行入口与当前阻塞项

执行顺序：Master Plan → 本文件 §8/§13 的依赖顺序 → 当前工作包对应的专项合同与验收记录。文档是目标，当前代码和新的验证日志才是完成证据；历史审计记录不能证明修改后的工作区仍通过。

历史快照：2026-09-27 曾发现 `multi_agent/mod.rs` 已声明 `source_coverage_decisions`，但对应文件不存在。**2026-09-28 复核时该文件已经存在，并有独立覆盖 Reviewer、交付和不可变裁决逻辑；“缺模块文件”不再作为当前阻塞项。** 本地新任务注册入口已更新为 v4；CI、findings、导出与 UI 已有覆盖裁决消费代码（详见 §3.1），不能要求从零重复实现，也不能将代码存在视为端到端能力已验收。须按最新专项审计核对零候选、恢复、CI、导出、聊天及 UI 的回归状态；本产品设计文档本身不构成测试或安装包已升级的证据。

因此交给 Qoder 的首项要求是：先收口当前源码覆盖审查的未完成变更，验证注册、派发、落库、独立审查、恢复、结果消费的完整一致性，并重新运行相关测试与质量检查；随后继续 P0 其他遗留项。不得为了让编译通过而删除未完成安全合同、伪造审查成功或关闭测试。P0 没有可信验收之前，不并行开启主机执行器开发来掩盖现有缺口。

源码按需模式进入 P1 时，先证明工具档零模型调用，再证明辅助/深度档的独立裁决及整体覆盖状态正确；主机离线 MVP 最后进入 P2。此优先级不阻止补充设计，但主机页应保持隐藏或“规划中”，不能先宣传为可用。

## 15. 少量 Windows/Linux 设备：首版产品范围与执行卡

本节是建议采用的产品规格，所有待开发项保持未完成；不新增主机执行授权。优先级继续按 §8：现有链路收口 → 按需协作 → 主机离线 MVP → 按需远程采集。

### 15.1 产品定位与首版模板

产品定位为“安全部门的小型主机检查与整改复测工作台”，不是终端管控、EDR、资产自动发现或自动化渗透平台。Windows 与 Linux 共享资产和报告模型，各自有采集器、规则与明确的支持矩阵。首版只实施前两个模板，其余按实际需求扩充：

| 模板 | 主要用户与输入 | 首版输出 | 排期 |
| --- | --- | --- | --- |
| Windows 工作站基础检查 | 部门自有工作站；人工采集包 | 防火墙、审计、账户策略、防护状态、服务配置的规则结果与整改建议 | P2 首批，限实机验收版本 |
| Linux 工具机基础检查 | 部门 Linux 工具机；人工采集包 | SSH、sudo 策略元数据、服务、防火墙、选定文件权限元数据 | P2 首批，限实机验收发行版 |
| 服务器上线前检查 | 另行授权的业务服务器；基础快照和指定服务配置 | 服务器基线与服务配置差距，可关联 Web 任务 | P2 后续，按服务逐项验收 |
| 实验环境前后对比 | 可回滚实验机的两份快照 | 选定配置变化、不可比较项和风险变化 | P2 后续，不提供攻击执行器 |
| 漏洞通告专项排查 | 已导入软件清单和版本化风险资料 | 疑似受影响资产、适用条件、待验证事项 | 后续，不用版本匹配冒充漏洞确认 |

首批规则数量由可验证性决定，不以“内置数千规则”为交付标准。每条规则必须提供平台适用条件、字段依赖、权限要求、证据路径、结果映射、修复建议、误报条件和测试夹具。权限不足、字段缺失、版本不支持各自有原因码，不能落为通过或不适用。

软件/补丁库存可以先展示事实，不必首版同时建设在线漏洞情报平台。选择少量明确支持版本；其余平台允许保存外部材料，但页面不得显示为已通过基线检查。

### 15.2 三种 Agent 的命名必须区分

1. **采集器/执行节点**：读取被冻结的字段、返回证据；不自主规划、不接收模型任意命令。人工采集器可以运行后退出，首版不安装常驻服务。
2. **AI 分析者**：解释材料、关联风险、提出下一步建议；默认只读经脱敏证据，没有目标主机连接权限。
3. **独立 Reviewer**：核对候选结论和证据、指出缺口；有独立身份和真实 assignment，不以多发一条聊天消息替代审查。

设备数量不决定 AI 数量。一个 Windows/Linux 批次可以由规则流水线逐机检查，再由一名分析者分批解释；只有明确的问题需要时才创建对应平台专家和 Reviewer。专家读取批次内的指定资产材料，不能获得整个公司资产库访问权。

### 15.3 模式矩阵及协作升级条件

下表角色为职责示意，实际运行时名称与权限必须经过合同评审，不按表格直接批量创建角色。

| 模块 | 日常模式 | 值得启用深度协作的条件 | 不应发生的行为 |
| --- | --- | --- | --- |
| Web | 有界工具与浏览器检查，必要时 AI 分析 | 多身份业务流程、相互矛盾的运行证据、明确的多条验证分支 | 每个 URL 固定拉起整套专家 |
| 源码 | 工具检查；按需解释候选 | 跨模块数据流、复杂鉴权、跨服务依赖，需要不同材料验证一个假设 | 每个文件分配一个 Agent，或为普通规则扫描制造群聊 |
| 灰盒 | 对齐版本/部署的源码证据与 Web 证据 | 代码候选需要在已授权部署中验证可达性或前置条件 | 从仓库注释或接口字符串直接取得线上权限 |
| CI/CD | 冻结策略的确定性检查 | 高风险变更中有明确且有预算的复核问题 | 等待群聊无限讨论，或模型超时默认放行 |
| 主机 | 离线采集、平台规则、可选单分析者 | 多项配置冲突、复杂服务依赖、跨资产风险关联且资料齐备 | 一台机器一个常驻 AI，或让专家自由操作主机 |

进入深度协作前，调度器必须逐项验证：有明确问题；材料在本次范围内；现有结果不足以回答；新增角色有独立职责；剩余预算可支付；有可测试的结束条件。符合条件只是允许提出分工，不能越过冻结模式和必要的人工确认。默认不并行重复扫描相同输入。

“AI 辅助”允许只做解释，不强制每次调用 Reviewer；此时必须标为解释/建议，不能标“已独立确认”。若要升级为正式 AI 确认，才进入独立复核链。模式选择不改变已有工具结果，也不替代当前合同明确要求的总体覆盖审查；未执行的审查只能显示“未执行”，不能伪造成功。

源码工具档未启用模型时，用户仍可输入筛选、查看和提出分析请求；系统展示“当前为工具模式，需要新建关联分析/批准升档”，不能因为用户发了消息就偷偷调用模型。升档只创建新冻结合同或新 attempt，保留原轮次结果。

### 15.4 主机页与任务历史的最小交互规格

主机模块首屏是设备/批次工作台，而不是聊天窗口。主操作为“登记资产”“查看采集说明”“导入采集包”“比较复测”；远程连接在未交付时不出现可操作按钮。

- **资产列表**：资产别名、平台、用途、负责人、最近成功采集时间、最新评估状态、待整改数和未知数。硬件标识等敏感字段按权限展示；不因 IP 相同就合并设备。
- **批次列表**：名称、选择的资产数、已评估/失败/待导入数量、规则版本、创建时间、负责人。汇总跳转到对应资产，不隐藏失败分支。
- **单资产详情**：概览、检查项、证据、整改/复测、关联任务、协作/执行记录。工具模式默认折叠协作页；所有模式都能看到真实检查进度。
- **检查项详情**：规则和版本、适用条件、期望值、观测值、采集权限、证据、结论来源、建议、复核记录；“规则失败”与“AI 确认漏洞”分开标识。
- **完成任务**：进入统一任务中心，按类型/资产/状态筛选。归档仅改变列表可见性，不删除报告；复测创建新任务并引用旧任务，不续跑归档 attempt。

基础状态至少区分待导入、校验中、评估中、等待人工、完成、部分完成、失败、取消；精确状态名须与既有任务状态机兼容，不另造一套互相矛盾的终态。采集流程状态、规则结果、AI 审查状态分别存储。

**汇总示例（仅示例数据）**：两台设备各计划 10 项检查，Windows 8 通过/1 不通过/1 未知，Linux 6 通过/2 不通过/2 未知。展示“2 台已评估，14 通过、3 不通过、3 未知”，不可展示“85% 安全”。覆盖率若采用“可判定检查数/适用检查数”，示例为 17/20；同时说明不适用项如何排除，缺失采集和未知不能从分母消失。规则去重键包含资产、快照、规则与版本，不能把两台机器上的同一规则合并为一条已修复发现。

### 15.5 数据复用、报告关联和整改规则

建议采用“批次 → 资产评估任务 → attempt → 快照/规则结果/证据/可选 AI 裁决”的关系；批次只负责汇总，不承担各资产共同授权。具体表名和迁移由现有 schema 评审确定，避免复制已有任务/证据表。

- 每个快照绑定资产、平台、采集器版本、profile、采集时间、导入时间、包摘要和来源可信等级。
- 每条结果绑定快照、规则版本和证据引用；AI 新判断作为带来源的追加记录，不能覆盖原始规则结果。
- 复测时规则版本/采集范围不同，先标记可比项和不可比项；不可比较不能计为修复。人工声明已修复与证据证实已修复分开显示。
- Web/源码/主机任务通过显式关联共享经批准的证据摘要，不共享会话、凭据、执行权限。源码仓库、部署服务、物理主机是不同实体，可人工确认关联，但不能仅靠 IP/路径推断为同一资产。
- 既有 JSON 原文、来源和历史报告仍保留；通过版本化适配器映射展示。旧 JSON 没有主机字段时按缺失处理，不硬补平台、签名、采集权限或 AI 审查结果。

整改首版只提供建议、负责人、状态和复测入口，不自动改配置。AI 从任务中总结的内容先进入知识候选；同类规则问题合并到既有知识主题，不为每台机器新建一份 skill，不保存可执行授权和秘密。

### 15.6 性能与失败设计：少量机器无需重平台

首版建议以每个控制端同时处理一个采集包、每个目标一个采集进程起步，平台分析按预算排队；这些是待测默认值，不是当前已实现能力或性能保证。大包解压/解析/规则执行不得阻塞 UI 主线程；达到内存、时间、输出上限后保留失败原因和已验证材料，不部分发布为成功结果。

AI 并发、规则并发、目标采集并发、浏览器并发各自限额，不能把“两个 Agent”理解成“最多两个操作系统进程”。缓存只复用校验过的工具/规则和只读材料，不复用前次目标凭据及可写工作区。离线材料分析不需要为每个 AI 创建虚拟机。

性能验收报告至少记录：控制端配置、目标平台、包大小、规则数量、冷/热耗时、峰值 CPU/内存、进程数、取消到退出耗时、失败回收结果。为运行时与测试进程分别采样；不能用修改 Agent 步数或 `nice` 代替实际资源上限。具体阈值先在试点机器上测量，再作为可配置且有边界的产品默认值发布。

单项无权限/缺字段继续其他合法检查并记录未知；导入完整性错误拒绝整包正式发布；授权撤销停止相关执行；未知执行结果进入核对而非自动重试。禁止把这些情况统一折叠成“扫描失败，请重试”。

### 15.7 交给 Qoder 的分包验收卡

以下均为待验收项，不得因为文档已存在而勾选完成。每项交付必须包含实际改动路径、迁移/兼容说明、测试命令与结果、已知限制；先更新现状差距，不重复实现已有模块。

- [ ] **P0 / 现有链路收口**：按当前源码和 Master Plan 核对真实缺口，特别是 v4 覆盖裁决到 CI、findings、导出、UI 的消费一致性；不以“文件存在”作为启用默认 v4 的依据。完成相关专项与规定质量检查。
- [ ] **P1-A / 模式合同**：新增模式字段及兼容迁移，覆盖创建、冻结、恢复、取消、重新运行；旧 attempt 不升级权限。工具档覆盖页面打开、导出、消息输入与恢复后仍零模型调用。
- [ ] **P1-B / 模式展示**：三档分别展示工具进度、辅助卡片、真实协作时间线；假角色消息测试应失败。用户提案必须显示真实受理/拒绝/等待确认回执。
- [ ] **P2-A / 主机格式与模板**：完成两平台首版支持矩阵、采集字段白名单、规则元数据、包上限及来源可信模型；外部 JSON 的命令/角色/权限字段不能触发执行。
- [ ] **P2-B / 手动采集与导入**：分别在受控 Windows/Linux 实机或虚拟机验收采集、低权限、敏感字段排除、超时和取消；导入覆盖损坏包、重复包、错误归属、恶意路径及事务失败。单平台未验收则只发布已验收平台。
- [ ] **P2-C / 检查与复测 UI**：完成资产/批次/单机详情、未知分母、部分失败、历史归档与可比性测试；使用 §15.4 的混合结果示例做汇总回归，不把无证据变成通过。
- [ ] **P2-D / 可选 AI**：规则检查不依赖模型；模型不可用时能查看报告；解释和正式审查分离，Reviewer 有真实独立交付证据；不增发主机 capability。
- [ ] **P3 / 是否引入远程采集**：先统计人工采集频率、耗时与遗漏，再决定是否做；尚无明确维护成本时保持手工采集。连接器另做权限、凭据、身份验证和支持版本评审，默认关闭。

**可直接给 Qoder 的执行指令**：以 Master Plan 为总约束，以本文件 §8、§13、§15.7 为产品顺序。先核对现状并完成 P0，不启动主机执行器；再实现源码按需模式及真实 UI；其后才做 Windows/Linux 手工采集和离线评估。不要实现通用主机 shell，不用群聊替代真实 assignment，不删硬授权/资源控制，不自动联网下载缺失工具，不把旧 JSON 变成执行授权。每个工作包必须独立给出可复现的验收证据；未交付功能保持隐藏或明确标记规划中。

## 16. 本轮决策补充：跨模块组合不是一个无限权限的大任务

本节为新增设计要求，不是已实现声明。沿用前述主机低优先级，不开启远程主机能力，不要求为每台机器部署常驻 AI。

### 16.1 先交付哪一条用户路径

1. **现有任务可靠结束**：先收口 Web/源码的任务状态、真实证据、人工指令路由、取消恢复、资源回收和报告一致性。不把预算暂停误报为扫描完成，不通过删除授权与资源控制解决中断。
2. **源码按需分析**：实现工具检查、辅助分析、深度协作的后端合同及全链路消费，再做创建页和聊天展示。当前 `native_source_coordinator.rs` 中新分析路径仍会依次准备 RepoMapper 与 SourceAnalyst 子任务，并进入候选/覆盖复核；不能宣称已有零模型工具模式。复入恢复分支与新分析路径分别验收。
3. **灰盒与 CI/CD 复用已可靠能力**：先把源码、部署与证据关联准确，不复制另一套扫描引擎，也不要求每次流水线启动一个聊天团队。
4. **主机离线 MVP**：等上述里程碑验收后，开展 Windows/Linux 手工采集、规则评估与复测。远程采集单独决策，不是首版必要条件。

### 16.2 一个业务系统的联合评估示例

假设用户持有一个源码仓库、一套已授权测试 Web 部署和两份已授权主机采集包。创建一个“联合评估”分组，引用以下独立任务；分组是关联与汇总容器，不签发统一无限权限：

| 子任务 | 默认策略 | 可以贡献的材料 | 不能据此获得的权限 |
| --- | --- | --- | --- |
| 源码检查 | 工具；疑点按需 AI | 固定提交上的路由、候选代码位置、依赖证据 | 访问代码中出现的任意线上地址 |
| Web 检查 | 有界工具与按需专家 | 已授权目标的实际请求、响应与浏览器证据 | 登录操作系统、检查同网段其他设备 |
| 灰盒关联 | 对齐后按假设派发 | 同一版本/部署的代码假设与运行证据关联 | 把静态风险直接升级为已利用漏洞 |
| 主机评估 | 导入包、规则；按需解释 | 对应设备在采集时间点的配置与组件证据 | 远程执行、修复或自动安装工具 |
| CI/CD 检查 | 冻结流水线策略 | 本次提交的增量结果与策略裁决 | 借用手工任务的审批或静默改变发布规则 |

“源码候选 → Web 验证”是显式依赖边：至少绑定源任务/attempt、候选证据、仓库提交、部署身份及匹配依据、目标任务/attempt 和授权引用。版本或部署无法对齐时，只能输出关联假设，不能记为已验证。

源任务失败时，依赖该证据的验证分支等待或标记不可执行；独立 Web 检查仍可继续。没有主机采集包时，主机分支显示未开展，不阻塞合法 Web/源码分支。联合汇总保留每个分支的覆盖缺口，不因其他分支成功而显示“全部通过”。

### 16.3 联合任务里的聊天和人工引导

- 项目群显示跨任务的摘要、待决策事项与证据引用；子任务线程显示真实 assignment、工具活动、专家交付与 Reviewer 裁决。工具日志不能伪装为 Agent 对话。
- 人工输入先解析为草案，明确接收任务、attempt、目标及线程；多个可能接收者时要求选择，禁止按最近更新时间猜测。确认使用草案冻结的绑定，不因另一个任务活跃而改投。
- “请优先核验登录鉴权”只在当前冻结范围内调整合法工作；“顺便检查这台 Linux”创建独立主机草案，展示缺失材料/权限，不立即执行。
- 工具模式中允许筛选、查看状态和提交升档请求，但不能因收到聊天自动调用模型。解释请求涉及新模型费用时，展示预计范围与预算，再进入明确的分析合同。
- 状态至少区分草案、待确认、已排队、实际受理、执行中、完成、拒绝/无法执行；最终状态名称复用现有合同。用户看见消息不等于执行器已接受，更不等于指令已完成。
- 各执行角色保有独立预算与回执；汇总角色只读经授权的脱敏材料，不拥有所有子任务的执行凭据。模型间“互相同意”不能代替独立证据和执行前校验。

### 16.4 发布前必须增加的跨模块回归

- [ ] 工具模式的源码任务从创建到导出，模型调用计数为零；恢复、打开聊天和读取报告也不例外。
- [ ] 深度源码任务真实交付独立子任务；普通工具结果与 AI 结论均保留原始来源，不互相覆盖。
- [ ] 联合评估内两项任务同时活跃，消息仍准确到达选定线程；歧义请求不写入可执行队列，确认不改投。
- [ ] 主机功能关闭时，Web/源码/灰盒任务照常运行；关闭开关不删除历史主机报告。
- [ ] 源码提交与部署不匹配时，跨任务关联只呈现假设；不能生成“运行验证成功”。
- [ ] 单个子任务取消、预算耗尽、材料缺失时，独立分支保留结果，依赖分支得到明确原因；不得伪造联合完成。
- [ ] 导入旧 JSON 不新增目标访问能力、角色身份或审批；同名 IP/设备不自动继承授权。

交付报告必须分别写“设计已完成”“代码已接入”“自动化验证通过”“真实平台已验收”，不得合并成一个完成勾选。本次仅补充设计与核对源码入口，没有执行这些待开发验收项。

### 17.2 实施合同

1. **明确动作域**：先区分说明/进度查询、当前范围内的分析偏好、规则或证据范围变更、目标执行请求。源码分析偏好只能作用于已冻结仓库材料；工具档查询不触发模型，模型解释请求须进入显式关联分析合同。不能把源码路径当成 Web 队列目标。
2. **阶段边界消费**：在尚未派发的阶段前受理合法建议；已冻结、已派发或已完成的阶段不改写输入。用户在模型请求进行中发来消息，应显示等待可用阶段或无法作用的明确原因，不显示“该模型已收到”。候选和覆盖 Reviewer 只能接收合法任务重点，不接受“认定它是漏洞”等预设裁决。
3. **持久化实际作用**：每条被采用的指令记录 scan、attempt、root、directive、阶段、输入修订摘要，以及实际采用它的 assignment/child-run。输入快照和阶段受理动作必须具有原子边界；命令入队、执行器领取、发送模型、完成交付分开记录。遇到未知外部调用结果，进入核对状态，不凭重试制造第二次调用。
4. **恢复保持原事实**：恢复读取已经冻结的输入与回执，不重新解释旧指令，不修改既有裁决/覆盖摘要。新建议只能绑定剩余合法阶段；所有阶段已结束时提示新建关联分析或新 attempt，原任务只读归档。
5. **扩大范围重新授权**：新增仓库、扩大目录范围、改变规则合同、要求访问 URL 或进入主机操作都不作为普通聊天即时执行。依现有合同进入审批/新 attempt/独立任务；Web、主机权限不能由源码 Coordinator 继承。
6. **前后端如实反馈**：复用现有指令状态机；新增源码阶段信息前先完成版本与迁移评审。未受支持的动作返回结构化原因并保留用户输入/历史。不得通过关闭整个聊天入口、统一标记完成或只追加一条“收到”消息伪装实现。

### 17.3 验收卡

- [ ] 在 SourceAnalyst 派发前确认合法关注点；冻结请求中确实含该引导，并可由 directive 追到真实 child-run 和交付回执。
- [ ] 在该请求执行中提交新建议；旧输入摘要不变，UI 不提前报告已应用；仅剩余合法阶段可采用，否则明确无法应用。
- [ ] 任务在受理/冻结/模型提交/交付各边界中断恢复；不重复应用、不重复派发、不篡改旧裁决，不把未知结果标成成功。
- [ ] 两个源码任务、一个源码与一个 Web 任务并发时，不串任务、attempt、root 或目标；stale fencing 拒绝写入，不让另一 Coordinator 代收。
- [ ] 源码只读建议不能新增网络或主机 capability；伪装在源码注释、模型回答或历史 JSON 中的指令同样无权升级。
- [ ] 普通解释、任务完成、证据不足、动作不支持、预算耗尽分别有真实可追溯回执；报告与聊天一致。
- [ ] 后续工具模式接入后，打开聊天、查询进度、恢复、导出全程仍零模型调用；有费用的解释请求独立确认，不能偷偷升档。

验收应使用本地数据库、受控模型替身和固定源码夹具先证明输入与回执关联，再验真实桌面 IPC。此工作包不需要连接用户给出的外部 URL，不需要 Windows/Linux 远程主机或 Kali。

## 18. 小规模混合设备的落地决策与资源调度

本节将上述产品决策收束为实施约束；不代表代码已支持配置项或下列行为，也不要求现在开发主机功能。

### 18.1 先问设备用途，再决定是否创建任务

| 实际需求 | 所属位置 | 首版动作 | 不应发生的行为 |
| --- | --- | --- | --- |
| 用部门 Linux 运行浏览器、源码工具或沙箱 | 环境管理／执行节点 | 检查已安装能力、资源与任务隔离 | 因节点接入自动扫描这台机器自身或所在网段 |
| 用 Windows 操作产品、查看报告 | 控制端 | 正常创建和查看任务 | 强制安装主机采集服务或常驻 AI |
| 检查 Windows 工作站自身 | 主机安全评估 | 人工运行已审阅采集器，导入、评估、整改复测 | 默认启用远程登录、修改策略或提权 |
| 检查 Linux 工具机／业务服务器自身 | 主机安全评估 | 按用途选择基础检查 profile，单独确认目标 | 复用扫描节点权限或 Web 登录态 |
| 对一套业务系统联合检查 | 项目中的联合评估分组 | 关联源码、Web、可选主机任务的证据 | 为汇总 Agent 发放全部子任务凭据 |

同一机器可以同时是执行节点和评估资产，但必须是两个职责记录，分别有身份、权限和生命周期。首版不要求建设远程节点集群；环境登记不能被实现为默认开启远程派发。

### 18.2 多 Agent 配额不等于工具并发配额

采用三个独立预算：模型调用／费用预算、控制端及执行节点的 CPU/内存/进程预算、对目标的请求／采集预算。一个 Agent 启动多个工具同样受限；多个 Agent 也不能各自获得一份完整机器资源上限。

- 少量设备的建议初始策略：每节点一个重型工具作业、同一目标一条有副作用可能或高负载的执行链；其余工作排队。具体阈值由本地基准测试决定，不承诺固定启动时间或 CPU 百分比。
- 只读模型分析可与工具工作重叠，但受独立模型预算约束；新增专家必须引用尚未解决的问题，不能仅因存在空闲槽位就启动。
- 能力匹配至少包含目标平台、工具／规则版本、隔离能力、可用资源和批准的执行位置；不匹配显示“缺少能力”，不得静默转发到任意机器。
- Windows 采集器需在已支持的 Windows 环境验收；Linux 容器中的 JSON 解析成功不能证明 Windows 实机采集成功。仅有一台 Windows 时可以顺序完成试点，不要求一角色一虚拟机。
- 共享可审计的只读工具缓存和镜像；任务工作目录、秘密、浏览器会话及可写临时文件按任务隔离。设备可以复用，前次任务的授权与可写运行状态不能顺带复用。
- 节点离线、资源不足、缺工具分别显示原因。等待资源不耗尽“无进展推理轮次”；但仍遵守用户约定的总截止时间。到期给出缺口或可恢复状态，不无限挂起。

以上是未来调度合同，不应通过取消现有硬预算实现。上线前分别验证单 Agent 多工具与多 Agent 多工具的总量限制，以及取消后的进程回收。

### 18.3 统一协作入口，按任务需要渐进展开

创建页默认展示目标、范围、模式与预算，不要求用户先理解角色编制。源码和主机默认工具模式；Web 按需分工；灰盒复用两侧任务并增加关联验证；CI/CD 默认无人值守的确定性检查。深度模式须明确显示额外成本和批准范围。

源码的一次日常检查可以完全没有 LLM；用户要求解释时创建关联分析，只有需要正式 AI 确认才追加独立复核。工具检查结果可按冻结策略阻断 CI，不必为了出现“Reviewer 已通过”而额外调用模型。反过来，未执行 AI 复核不能被报告成已经复核。

聊天只在存在真实 AI 工作时显示对应成员活动；用户仍可从所有模式进入“提出分析请求”。内部通信保留任务指派、必要摘要、证据引用和结果回执，不要求展示模型私有逐步思考。用户的建议必须得到接受、待确认或拒绝的可追溯反馈，不能变成无人消费的一条群聊消息。

### 18.4 进入主机开发的门槛和验收责任

先完成 §15.7 的 P0、P1，并对灰盒和 CI/CD 的已有关键路径提交回归证据；经产品确认进入 P2 后才实现主机离线 MVP。远程采集、常驻服务和自动整改不在同一工作包中。主机相关设计可以先定稿，但不能挤占当前执行正确性与性能修复。

Qoder 的每个工作包必须给出“实现／未实现／未验证”清单；由可复现测试或明确的实机试点记录支撑，不凭设计文档或 UI 截图交付。除 §15.7 的验收卡外，追加以下待验收项：

- [ ] 同一物理机双重身份不会继承另一职责的权限；登记执行节点不会创建获准主机目标。
- [ ] 一台 Windows、一台 Linux 的混合批次允许顺序处理；一台离线不阻塞另一台完成和归档。
- [ ] 源码工具模式从创建、扫描到导出和恢复全链路零模型调用；关联 AI 分析单独计费、留痕。
- [ ] 两个 Agent 同时申请工具时遵守节点总量限额；排队、取消、超时后不留孤儿作业。
- [ ] 联合评估中主机未开展只显示覆盖缺口；Web、源码任务可独立结案，汇总不能显示全范围通过。
- [ ] 主机入口处于规划中时，直接调用后端启动接口同样不能执行主机动作。
