# 业务前端深度分析（默认流程）

这份 Skill 把日常人工测试习惯变成一条可解释的自动化流水线。Oviraptor 负责确定性采集、还原、去重和排序；Strix 只处理已经具备请求、参数或代码证据的少量候选。目标不是“扫得多”，而是尽快给出能继续验证的高价值信息，并在没有新信息时明确结束。

## 输入与职责边界

- 首先读取 `frontend-evidence.json`。其中的 `surface`、`investigation`、`opportunities`、`apiCandidates`、`apiIntelligence`、`requestHeaderIntelligence`、`verificationPlan` 和 `stopRule` 是本次任务的事实入口。
- `investigation.modelGate=false` 表示本地信息增益门禁未通过：除普通服务端 Web 的首次一次性兜底外，不启动开放探索。`investigation.hypotheses` 是唯一允许交给模型的验证队列。
- Oviraptor 已经完成页面渲染、开放 Shadow DOM/同源 iframe 探索、有限路由访问、动态菜单/标签/详情控件触发、交互与网络请求关联、业务 JS 分类、AST 常量传播、接口字符串拆分与证据化重组、请求头契约、指纹归类和安全 GET 验证。不要重复这些工作。
- JS 重组得到的 URL 仍是候选。只有 `validated=true`、运行时真实请求，或新的请求/响应工具验证成功，才能称为真实接口。
- 指纹只用于选择测试方法和本地知识，不把“某框架/某版本/某路径存在”直接当成漏洞。

## 默认测试流程

### 1. 看功能

从 `runtimeExploration.features`、`businessEntrypoints` 和最高分 `opportunities` 理解页面能做什么。优先关注登录、注册、找回密码、用户/角色/权限、详情、搜索、导入导出、文件、订单、支付、配置、审计和管理功能。

不要为了“看全”而遍历整站。一个功能只有在产生新状态、新请求、新参数或新的业务入口时才算带来信息增量。

### 2. 把点击和请求对应起来

优先使用带 `actionId`、`stateId`、`feature` 的运行时请求。恢复并保留：

- HTTP method、完整 URL、状态码和内容类型；
- Query、JSON/Form Body 参数名与请求形状；
- `requestHeaderNames` 中运行时真实生效的请求头名称，以及 `extraRequestHeaderNames` 中由 CDP ExtraInfo 补全的浏览器层请求头；
- 触发它的页面状态、控件文本和动作；
- 写请求只读取已捕获的请求形状，不自动重放提交、创建、删除、支付、上传等动作。

### 3. 深入业务 JS，但只补证据缺口

先使用 AST 已还原的请求。查看 `apiIntelligence` 时按以下可信度理解：

1. 运行时真实请求：最高可信，直接作为验证基线；
2. fetch/XHR/axios 调用经过常量传播得到的 URL：高可信；
3. 明确的 baseURL/apiPrefix 与业务路径组合：中高可信；
4. 至少两个真实请求支持的公共前缀与业务路径组合：中可信；
5. 单独出现、没有客户端或运行时前缀证据的字符串：只作搜索线索，不请求。

`origin + apiPrefix + businessEndpoint` 必须保留各自的证据来源。禁止把任意域名、前缀和字符串做笛卡尔积，禁止把前端路由误当 API。

只有某个高价值候选缺少一个明确依赖时，才按 `frontend-code-index.json` 读取最多三个局部代码切片；优先 dependency-definition/http-client，再读关联 network-call。不要读取完整压缩包或全部切片。

### 4. 形成可验证的接口契约

将候选整理成：`功能 → 动作 → method → origin → apiPrefix → businessEndpoint → 参数 → 请求头契约 → 认证状态 → 响应`。

请求头必须分层：`requestHeaderIntelligence.observed` 是运行时事实，`declared` 是 JS 中明确声明但待运行时确认的契约，`possibleBrowserManaged` 只是 Host/:authority、Content-Length、Cookie、Origin、Referer、Sec-Fetch-*、Sec-CH-UA-* 等可能由浏览器管理的提示，未观察到时不能当作目标真实请求头。模型证据包只给请求头名称；复现时从当前授权会话重新取得实际值，不从历史知识复制 Cookie、Token 或 Authorization。

优先验证：

- 对象 ID、用户 ID、租户/组织 ID 和角色/权限边界；
- 未登录与已登录、普通用户与高权限用户之间的响应差异；
- 文件名、路径、URL、回调地址、查询条件、导出条件等可控输入；
- 前端限制与服务端实际限制不一致；
- 客户端加密/签名仅作为还原请求的步骤，不把“使用了加密”当问题。

没有新请求/响应证据时，不基于接口名称猜测漏洞。

### 5. 低成本指纹与本地知识匹配

仅识别产品族、后端技术族和明显组件，例如 Django/Python、Spring/JVM、PHP CMS、Node、若依类管理系统。没有稳定特征时保留“未知/候选”，不消耗模型去穷举具体产品和版本。

本地 Wiki、方法卡片或 PoC 只有在目标指纹、路径/参数契约和适用前提同时匹配时才进入验证。公开版本匹配、NVD 命中或文件名命中只能标记为 `dependency_signal` 或 `needs_verification`。

### 6. Strix 只验证最高价值候选

- 从 `investigation.hypotheses` 中 `decision.eligibleForModel=true` 的最高分项开始，一次只处理一个候选；旧结果没有调查假设时才兼容读取 `verificationPlan.primaryCandidate`。
- 必须逐项遵守 `contract.requiredEvidence`、`contract.maxAttempts`、`contract.mutationPolicy` 和 `contract.stopRules`。缺少控制请求、对比响应或影响证据时，不得把候选晋升为漏洞。
- 多身份差异只是权限候选。必须复用同一 method、URL、请求形状和业务对象上下文，取得控制身份与对比身份的响应证据；单纯状态码不同或某身份看不到接口不等于越权。
- 复用证据包中的 method、URL、参数和触发上下文，不重新爬站、不重新枚举 JS、不重新识别框架。
- 先做最小响应差异或权限边界验证；只有出现不同响应、越权迹象、可控数据流或安全影响时才继续 PoC。
- 复杂前端每个候选最多两次验证；两次都没有不同响应或安全效果，立即结束该分支。
- 不创建子 Agent，不用 todo/笔记/报告回合代替测试，不把普通接口、公开 JS、缺失安全头或技术栈暴露写成漏洞。

### 7. 没有高价值信息时的保底

只要 `surface!=static_frontend` 且 `boundedFallbackDiscoveryAllowed=true`，就允许一次小型目录/API 发现。是否兜底由证据增益决定，不依赖 Django、Spring Boot、若依或前端框架标签是否识别准确：

- 字典优先来自已观察到的 JS 词汇、产品族和业务名词；
- 只运行一个工具、一个有上限的词表、非递归；
- 单个或少量 401/403 记录为认证/角色边界，跳过相同拒绝请求并继续其它在范围功能；只有明确回到登录页、所有可用身份都失效，或出现持续同质拦截时才停止；
- 出现明确 WAF/机器人挑战/验证码或持续 429 限速时立刻停止；
- 本轮没有新增真实端点、参数、指纹证据或高价值入口时结束目标；
- 禁止重复运行 ffuf、dirsearch、gobuster、feroxbuster、wfuzz 来碰运气。

`framework_application` 可在首次基线且没有可验证假设时使用上述一次兜底；`static_frontend` 不进入目录爆破。

## 输出格式

每个保留项都写清：

- 发现了什么，为什么值得继续；
- 功能/动作与请求的对应关系；
- method、完整 URL、前缀、业务路径、参数和请求头名称/来源；
- 证据来自运行时、AST、字符串重组、HTTP 验证还是本地知识；
- 当前状态是已观察、已验证、待验证、已排除还是已耗尽；
- 最小下一步，以及触发停止的条件。

漏洞结论必须包含可复现请求/响应、安全影响、适用边界、PoC、CVSS/CWE 和修复建议。没有漏洞时也要输出已覆盖的功能、已验证接口、未解决候选、停止原因和一条最值得人工继续的建议。

## 学习规则

- 学习只保存去目标化的方法，不保存域名、IP、Cookie、Token、请求头、凭据或原始业务数据。
- 事实与模型建议分开：事实来自请求/响应、代码位置和工具结果；模型只负责归纳标题、步骤和下一步。
- 单次模型输出先成为待审核候选，不直接改写 Skill。
- 同一模式至少由两个不同扫描任务支持，才可作为稳定的自动复用知识；同一任务换模型重复提炼不增加支持数。
- 知识分三层保存：`事实` 只能来自请求/响应、AST 位置、页面状态和工具结果；`策略` 必须由至少两个独立任务支持或一次已确认验证才能晋升；`结果` 同时记录成功、失败、耗尽和停止原因，避免后续模型重复走无效路径。
- 增量复测先比较 API 与参数签名。没有新增/变化证据时复用基线并停止，不因重新点击“扫描”就把同一份前端内容再次交给模型。
- 知识使用规范化键去重，模型名称、部署方式、提示词哈希和规范化版本必须保留，以便解释不同模型的差异。
- 应用候选时按 Markdown 章节确定性合并；模型不能覆盖未涉及章节。内置 Skill 永远不被学习流程直接改写。

## 最终停止条件

满足任一条件就结束当前 URL：

- 最强候选达到规定尝试上限且没有新证据；
- 证据只剩指纹、公开资源或猜测路径；
- 一次保底发现没有新增价值；
- 明确回到登录页且所有可用身份都失效，或出现持续限速/WAF/验证码拦截；
- 后续动作需要提交数据、创建对象、删除内容、支付、上传或其它未授权状态变化。

结束不是失败。应保留已有证据、未解决候选、成本和停止原因，让人工能从最有价值的位置接手。
