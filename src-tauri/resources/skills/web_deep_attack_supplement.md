# Web 深度攻击补充手册

本手册补充 secknowledge-skill（SQLi/XSS/RCE/SSRF/XXE/上传/反序列化/逻辑鉴权/AI 安全）之外、
最容易被漏测的四类面。遇到对应面时逐项核对；每条都要留下可重放的请求/响应证据，没有证据只记
`insufficient_evidence`，绝不臆断。任何一条确认问题，走 `record_hypothesis_result` 的 confirmed。

## 〇、执行纪律（最先读，决定能不能真出结果）

**recon 完成 ≠ 调查完成。** 列出接口、识别出指纹、抓到 JS，只是开始，不是结论。把 recon 的每一项
变成一次**带证据的测试**，否则这次扫描等于白跑：

1. **对每一个 recon 发现的业务 API / 端点，必须至少过一遍第二节**（鉴权缺失、越权、参数篡改）。
   不得只把接口登记进结果就收口——登记不是测试。
2. **识别到产品/框架（`tech_identified`，如本次的若依）时，先做第三节的定向核对**（特征端点是否
   暴露、是否未授权可达），再回到通用面。指纹命中却不做定向验证，是最大的漏测。
3. **有登录/认证面就过第一节**（账号枚举、验证码强度、鉴权逻辑、频率/锁定取证）。
4. **预算/轮次有限时按"高价值证据优先"推进**，但**收口前必须在覆盖账本逐条写清**：每个已发现端点
   测了哪些点、结果如何。0 发现要写成"**已测未发现**（测了 A/B/C，响应如何）"，**绝不能是"未测"
   或笼统写"安全"**。被预算/轮次打断而收口的，也要留下"已测哪些、还剩哪些没测"的清单。
5. 每一条确认必须绑定"**控制请求 + 测试请求 + 影响说明**"三件证据；缺一件只记 `insufficient_evidence`。

**真实证据铁律（最重要，不守这条结论必被打回）**：证据里的每一个 pocRequest / reproductionStep /
probe，**必须是你真实发出过、并有真实响应被捕获的请求**——绝不描述一个"假设会怎样"的 POC。要测
某个探测（如带恶意 Origin 的跨域、带他人 id 的越权、改金额的篡改），就**真的把那个请求发出去、
把响应留进证据**，再拿它和控制请求（正常请求）对比。候选 finding 里声称做过的探测，若证据中找不到
对应的真实请求/响应，该候选自相矛盾，只能 `insufficient_evidence`，不要提交。URL、pocRequest、
reproductionSteps 三者必须**指向同一个真实被测端点**，不得一个指文档、一个指接口。

**CORS 为例（示范"真实差分"长什么样）**：想判 ACAO 过宽，必须**真发两条请求**：①正常请求（无/正常
Origin）记录响应头；②带受控恶意 `Origin: https://evil.example` 的请求，看服务端是否**把该 Origin
原样回显进 `Access-Control-Allow-Origin`**，并是否同时 `Access-Control-Allow-Credentials: true`。
只有"恶意 Origin 被回显 + 允许携带凭据"才构成可被利用的跨源数据暴露（confirmed）；`ACAO: *` 且
无 Allow-Credentials 多为静态资源常见配置，不足以 confirmed。两条请求都要在证据里。

全程只做授权范围内、非破坏性的取证式验证：不 DoS、不破坏性写、不越授权范围。

## 一、登录 / 认证面深挖

登录口不是"有验证码就结束"，而是一个高价值攻击面。逐项核对：

- **账号枚举**：对比"登录 / 找回密码 / 注册"在用户存在与不存在时的响应差异（文案、状态码、
  响应时间、字段）。差异可枚举即为 user enumeration。
- **验证码强度**：验证码是否**仅前端校验**（直接带空/错值请求后端是否放行）；是否**可复用**
  （同一验证码多次提交是否通过）；是否**不失效**（换用例时旧验证码仍有效）；图形验证码能否
  OCR 稳定识别；滑块/点选验证码的校验参数是否可预测、是否有可解密的 key 或固定签名。
- **认证逻辑**：登录是否返回可预测/可枚举的 token；记住登录/自动登录的凭据是否弱；多因素是否
  可绕过（跳步、改响应、复用 OTP）。
- **频率与锁定（取证式，非轰炸）**：用**少量有界请求**探测登录 / 短信 / 邮件接口是否**缺少
  频率限制或锁定**。目的是证明"缺少防护"这一漏洞，而不是真的发起洪水；确认缺失即停、记录证据，
  严禁大量发送造成轰炸或 DoS。

## 二、已发现 API 接口的鉴权与逻辑滥用

对 recon 阶段发现的每个业务 API（pendingQueue 的 api: 项）逐个过：

- **越权（IDOR / BOLA）**：把资源 id、用户 id、订单号等换成他人的，看是否返回他人数据。
- **垂直越权**：低权限身份直接请求管理类接口 / 功能；未授权直达需要登录的接口。
- **参数篡改与批量赋值（mass assignment）**：提交未在表单暴露的字段（role、isAdmin、price、
  status）看是否被接受。
- **鉴权缺失**：去掉 Cookie/Token、换过期/他人 Token，看接口是否仍返回业务数据。
- **方法与内容型**：切换 HTTP 方法（GET↔POST↔PUT↔DELETE）、改 Content-Type、数组/对象注入，
  探测被忽略的服务端校验。

**越权的标准测法——两身份差分（最可靠，优先用）**：准备两个已认证身份 A、B（可用授权范围内的
测试账号）。对每个返回数据或改状态的接口：把 A 的请求里的对象引用（id/编号/部门/租户）换成 B 的，
看 A 能否拿到或改动 B 的数据（水平越权 BOLA）；再用低权限身份请求管理/高权限功能（垂直越权
BFLA）。**判定**：跨身份成功拿到/改动了不属于当前身份的数据或功能 = confirmed。只有一个身份时，
退化为"去掉/替换/过期 Token 后仍返回业务数据"的鉴权缺失测法。

## 二·五、业务逻辑 / 工作流滥用（企业系统高发，最易被漏测）

企业系统（订单、审批、工单、账务、权限管理）的高价值漏洞常在**业务流**里，而不是单个接口的输入
过滤。对识别出的业务流程逐项核对：

- **状态机跳步**：直接请求流程后段接口（跳过"审批"直达"执行"、跳过"支付"直达"发货/开通"），看
  后端是否校验前置状态与来源。
- **审批 / 权限变更绕过**：自助提权、改他人角色/部门/租户、把草稿越过审批直接置为生效。
- **金额 / 数量 / 价格篡改**：负数、超大值、小数精度、直接改总价/折扣字段，看服务端是否只信前端
  计算。
- **重放 / 幂等缺失**：同一"一次性"请求（下单、转账、领券、兑换）重复提交是否产生重复副作用。
- **并发 / 竞态（取证式）**：对一次性操作做**少量有界并发**重放,看能否突破限制；证明缺陷即停，
  严禁刷量或造成真实损失。

每条都绑定：**控制请求（正常流程）+ 测试请求（跳步/篡改）+ 影响说明（拿到了什么本不该有的结果）**。
涉及资金或不可逆操作的，只验证到"证明缺陷存在"即停，不真正造成损失或破坏。

## 三、识别到框架 → 已知公开漏洞复现

当指纹/`tech_identified` 认出了具体框架或产品（如 RuoYi/若依、Spring Boot、ThinkPHP、
Shiro、Fastjson、各类 CMS）时：

- 按**该框架的已知公开漏洞**定向验证其特征端点与利用点，而不是只做通用扫描。例如：Spring Boot
  的 actuator 暴露、Shiro 的反序列化/key、Fastjson 的 autoType、若依的接口未授权/SQL 等。
- 先探特征路径是否存在、是否暴露 → 再在**授权且非破坏**前提下做最小验证取证。
- 版本能定位时，对照该版本已知问题逐条核对；不能仅凭版本号断定"有漏洞"，必须有请求/响应证据。
- 没命中也要在覆盖账本写清"测了哪些已知点、为何未命中"，不得写成"安全"。

## 四、开源二开项目的上游比对分析

目标疑似基于某开源项目二次开发（二开）时：

- **定位上游**：从页面特征、静态资源路径、注释、报错、favicon hash、特有接口命名，推断其基于
  哪个开源项目及大致版本。
- **继承漏洞**：核对该上游项目的**已知公开漏洞**是否在二开版本中仍然存在（很多二开只改业务、
  不打安全补丁）。
- **改动引入的新问题**：二开常新增/魔改接口、放宽鉴权、硬编码密钥、调试开关。重点看二开新增的
  自定义接口与被改动的鉴权逻辑。
- 有源码或可下载构建物时，交给源码/构建物分析能力（source 扫描、artifact analyzer）做 Source-Sink
  与密钥/端点提取，再回到运行时验证。

## 五、遇到 WAF / 验证码时（先绕后停）

不要一遇到防护就立即收口。在授权范围内先尝试绕过：

- **WAF**：XFF / X-Real-IP / 其它来源头伪造、大小写/编码变形、分块/参数污染、备用原始 IP 直连。
- **验证码**：见"一、登录面"的仅前端/复用/失效/OCR/可预测性检查。

仅当多次绕过均失败、确认是硬性持续拦截时，才记录 `confirmed_waf_or_challenge` 收口。全程不做
DoS、不做破坏性或不可逆操作、不超出授权范围。
